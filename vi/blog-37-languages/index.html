给博客配了 37 种语言之后：多语言 SEO 的真实代价

如果你在这个博客的 URL 后面加一个语言前缀，会发现大部分文章都有几十种语言的版本。是的，这个站把每篇新文章自动翻译成 37 种语言。当初做这件事时我觉得自己酷毙了；跑了半年之后，我想诚实地聊聊它到底带来了什么——好的、坏的、和「早知道」的。

当初为什么想做这件事

起因很简单：博客的主要读者是中文用户，但我的文章偶尔会被分享到海外社区，于是萌生了「让更多人能读懂」的想法。加上 GitHub Actions 反正闲着也是闲着，就设计了一套流程：

  1. 新文章推到仓库；
  2. 工作流检测到 source/_posts/ 下的新增/变更；
  3. 调用翻译接口把中文原文翻译成目标语言；
  4. 写入 source/_posts/<语言代码>/ 子目录；
  5. 自动提交、触发部署，几分钟后线上就有新语言版本。

技术上的成就感是真实的：内容流水线自动化这件事，本身就很有趣。 而且一想到这个博客可能被几十种语言的读者阅读，那种「国际化」的感觉确实很爽。

跑起来之后，真实情况是这样的

翻译质量：比想象中好，但离「能用」还有距离

先说个公道话：现在的机器翻译质量，比我预想的好太多。技术类内容的翻译准确度相当高，术语、代码、链接这些基本都能正确处理。读者如果只是想「看懂大意」，完全够用。

但问题出在「只可意会」的部分：

  • 中文特有的梗、谐音、双关，翻译过去基本全军覆没；
  • 语气和情绪会变得平淡，一些我精心设计的表达，翻完像白开水；
  • 口语化、网络化的措辞，翻出来的味道总差那么一点；
  • 偶尔还会出现术语前后不一致的情况（同一篇文章里同一个概念被翻成不同词）。

我的结论是：机器翻译适合「传递信息」，不适合「传递风格」。 如果你的内容以信息量为主，多语言是加分项；如果内容靠文笔和个性吃饭，机器翻译版可能会让读者觉得「这作者水平一般」——因为你的文采在翻译里丢了。

SEO 的真相：hreflang 是标配，但效果存疑

做多语言站点，第一课就是 hreflang：告诉搜索引擎「这篇文章在哪些语言下有对应版本」，避免被当成重复内容。

理想情况下，配好 hreflang 之后，搜索引擎会按用户的语言偏好展示对应版本，还能避免「重复内容惩罚」。但半年跑下来我的体感是：

  • hreflang 配置本身不难，但要在主题模板里正确输出每篇文章的所有语言版本链接，需要一定的模板定制。
  • 搜索引擎对「机器翻译内容」的态度越来越微妙。 一方面它能识别出这是翻译内容，另一方面如果机器翻译质量一般、又缺乏原创性，在结果里的价值会打折。
  • 真正的流量增长有限。 我本以为 37 种语言能带来 37 倍的流量，实际上海外流量确实有增长，但远没有和语言数量成正比。英语、日语等少数几个大语种贡献了绝大部分海外流量，其余语种基本是「有人看，但极少」。

如果你问我「值不值」，我的诚实回答是：如果你主要是为了 SEO 流量，大概率不值；如果你是为了「让内容被更多人读到」的理想主义，那它是成立的——但请先接受它带来的维护成本。

内容仓库的膨胀：一个 37 倍体积的 repo

这是最实际的代价。原来一篇中文文章一个文件，现在一篇中文原文 + 37 个译文文件，仓库体积和提交频率都大幅上升。

伴随而来的是一系列连锁反应：

  • Git 历史变得嘈杂：翻译工作流每次都会产生大量提交，让 git log 变得很难读；
  • 容易误改译文：我一开始就定了规矩「只改中文原文、译文交给流水线」，但实际操作中还是出现过不小心改了译文目录的情况；
  • 触发循环的风险：翻译工作流提交之后，如果 CI 的触发条件没设计好，可能会形成「提交 → 触发 → 再提交 → 再触发」的死循环。我的做法是给工作流加触发过滤，避免「自己的提交再触发自己」。
  • 构建时间变长：37 种语言的文章全量生成，构建时间比单语言翻了不止一倍。

还有一个容易被忽略的问题：内容会「漂移」

中文原文改了，译文会自动重新生成吗？如果你的流水线设计成「每次全量翻译」，那没问题；但如果像我早期那样只翻译「新增或变更的文件」，就会出现原文和译文不同步的情况——某篇中文更新了，但译文还是旧版。

这个问题最隐蔽也最坑：你以为读者看到的是最新的，实际上海外读者看到的是几个月前的旧版本。 现在我的策略是「改动中文原文时，联动失效对应语言的缓存/强制重译」，但这又增加了流水线的复杂度。

如果让我重新选，我会怎么做

跑了半年，如果让我带着现在的认知重新设计这套多语言方案，我会这样选：

  1. 先做英文，别一上来就 37 种。 英语是海外流量的绝对主力，把英文版做好（包括人工校对关键词轮换），价值远大于铺 30 多个没什么人看的小语种。
  2. 把翻译质量分级。 英文版用质量更好的翻译（甚至值得人工校对）；小语种可以用便宜的批量翻译，定位就是「给看不懂英文的人一个读懂的机会」。
  3. 区分「核心内容」和「长尾内容」。 高价值的教程、评测类文章值得全文翻译；流水账、碎碎念就别翻译了，省点维护成本。
  4. hreflang 从一开始就配好。 别等上线了再补，模板定制要趁早。
  5. 给「只改原文」立好规矩和技术护栏。 译文目录只由工作流写入，人肉提交到译文目录的 PR 直接拒绝。

写在最后：技术很酷，但要想清楚「为什么」

回看这半年，我不后悔做多语言——它让这个博客真正意义上「走出去」了，也让我学到了内容流水线、hreflang、CI 触发设计这一大堆新东西。这些都是宝贵的经验。

但我也想诚实地告诉想抄作业的人：「支持 37 种语言」这个数字看起来很酷，但它更多是一种技术实现，而不是一种内容策略。 如果重来一次，我会先把「为什么需要多语言」想清楚，再决定要多少种语言——而不是先定一个很酷的数字，再让内容去迁就它。

技术的魅力在于「能做什么」，但做之前，最好先想清楚「该不该做、为谁做」。这句话送给所有正在被「看起来很酷的技术」诱惑的你，也送给我自己。
