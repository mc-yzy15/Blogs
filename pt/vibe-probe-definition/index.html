Vibe Coding 到底是什么：一次概念澄清

「Vibe Coding」大概是这几年被引用得最多、被定义得最少的开发术语之一。它第一次进入大众视野时，描述的是一种相当具体的行为：你不看代码，只凭感觉（vibe）描述你想要什么，让模型反复改，直到跑出来的东西看起来对了。但两年过去，这个词已经被厂商、媒体和招聘启事反复借用，如今既能指「用 Copilot 补全一行函数」，也能指「一句话生成一个 App」，甚至能指「产品经理自己搭了个内部工具」。

当一个词同时指代这么多东西，它就失去了沟通能力。本文想做的事情很朴素：把 Vibe Coding 和它最容易混淆的三个邻居——AI 辅助编程、低代码平台、提示词生成应用——放到同一张桌子上，用可操作的标准把它们切开。

为什么这个词一定需要澄清，以及从哪些维度澄清

概念含混不只是学术问题，它会直接造成工程上的误判。

第一类误判是风险误判。如果团队把「让模型补全单元测试」和「让模型不改测试直接改实现直到变绿」都叫 Vibe Coding，那么针对前者制定的代码评审流程，会被后者悄悄绕过——因为流程的假设是「人始终读得懂改动」。

第二类误判是能力误判。当招聘方写「熟悉 Vibe Coding」，他可能期待的是会用 Cursor 的 Tab 键，也可能期待的是能设计一套带自动验证的 agent 工作流。两者的技能栈和薪资区间完全不同。

第三类误判是归因误判。项目延期时，「我们用了 Vibe Coding」常常被当成一个方便的借口，而真正的问题可能是需求不清、缺少测试、或者压根没人做验证。

所以澄清这个概念，本质上是给不同风险等级的工作流贴不同标签，而不是给一个新工具起名字。

而这四个维度的观察方式，也给了我们一把通用的尺子。它们不是非此即彼的开关，而是连续光谱上的位置。

  • 控制权归属：最终决策由人还是由模型做出？人只在开头写一次提示，还是持续介入每一次修改？
  • 验证强度：变更是否被自动测试、类型检查、静态分析或人工评审拦截？
  • 代码可见性：使用者是否需要、是否能够阅读生成的代码？「不看」是一种选择，还是一种能力缺失？
  • 可复现性：同样的意图重新执行一次，是否大概率得到结构一致的产物？

把这四个维度套上去，几个概念的差异立刻清晰：AI 辅助编程的关键词是「辅助」，控制权在人，验证强度通常不变；低代码的关键词是「平台」，控制权在平台提供的抽象层，代码可见性低但可复现性高；Vibe Coding 的关键词是「意图先行」，控制权和验证强度同时被下放，代价是可复现性和可维护性。

与 AI 辅助编程的边界：控制权与验证是否被让渡

这是最常被混淆、也最需要切开的一对。

AI 辅助编程（AI-assisted programming）的典型形态是补全、改写、解释、生成测试、批量重命名。它的本质是加速人类已有的决策过程：人先决定要做什么、做在哪、做成什么样，然后让模型把机械劳动做掉。人始终在循环里，并且在每一步都保留了「读代码」的默认动作。

Vibe Coding 的典型形态则是：人给出一个意图，模型产出实现，人只观察外部行为是否符合预期，如果不符合，就追加一句描述继续改。这里发生了一个关键让渡——从「读代码判断对错」让渡到「看现象判断对错」。

这个让渡不是道德问题，而是工程权衡问题。它在以下场景是完全合理的：

  • 一次性脚本、数据分析、格式转换，产物用完即弃；
  • 个人原型、周末项目、演示 Demo，失败成本接近零；
  • 探索性任务，你连自己想要什么都不知道，需要先看到东西才能提要求。

它在这类场景则相当危险：涉及用户数据、涉及金钱、涉及对外暴露的接口、需要长期维护的代码库。

判断标准可以用一句话总结：如果你无法承受「没人读懂这段代码」的后果，那它就不是 Vibe Coding 场景，无论你用的是哪个工具。

与低代码的边界：抽象层方向相反

低代码平台和 Vibe Coding 都承诺「少写代码」，但它们实现这个承诺的机制几乎相反，这一点常被忽略。

低代码的路径是向上抽象。平台把常见需求固化成可视化组件、拖拽流程、配置项，你操作的是平台定义的语义单元。它的优势在于约束强：因为选项有限，所以产物可预测、可导出、可迁移，平台也敢对企业承诺 SLA。代价是天花板明确——一旦需求落到平台没抽象到的角落，你就要和平台打架，或者被逼去写插件。

Vibe Coding 的路径是向下生成。它不预设抽象层，直接产出通用语言代码，理论上没有天花板。代价是约束几乎为零：同样的提示，两次运行可能得到两种结构；命名风格、错误处理、依赖选择全凭模型当次判断。

用一个类比：低代码像住在精装修公寓，户型固定但水电煤气都通好了；Vibe Coding 像拿到一堆建材和一张手绘草图，理论上能盖出任何房子，但漏不漏水得自己验。

这带来一个反直觉但重要的结论：低代码的产物通常比 Vibe Coding 的产物更容易长期维护，哪怕前者的代码你一眼都没看过，后者你逐行读过。因为可维护性取决于约束的稳定性，而不是取决于你读没读过。

与「提示词生成应用」的边界：一次性产物还是可持续流程

第三个邻居是「提示词直接生成应用」。它和 Vibe Coding 高度重叠，但可以区分出两种不同性质的东西。

一种是产品化的生成器：你填一段描述，平台吐出一个完整的、可部署的应用骨架。这里的控制权其实在平台手里——平台决定了技术栈、目录结构、默认依赖。用户做的选择很少，因为选项被平台收敛过了。本质上这是低代码的一种极端形态，只是把「拖拽」换成了「描述」。

另一种是持续的对话式开发流程：你有一个真实的项目目录，模型读写其中的真实文件，你持续给出反馈，代码持续演化。这才是 Vibe Coding 的原始含义。区别的关键不在「是否用了自然语言」，而在产物是否继续被迭代。

这张表里最值得盯住的一行是「是否读代码」。它是这四个概念在实践中最容易被观察到的分水岭，也是团队做流程设计时唯一必须提前明确的一件事。

一个可操作的判定清单

如果你想知道自己手上的工作流到底属于哪一类，可以按顺序问自己四个问题：

  1. 我最后一次完整读过这段代码是什么时候？ 如果答案是「从没读过」，你大概率在做 Vibe Coding。
  2. 如果模型明天换了版本，产出变了，我有办法发现吗？ 如果没有自动化手段能发现，你的验证强度接近零。
  3. 这套产物需要活多久？ 一周和三年，对应完全不同的策略。
  4. 失败了谁承担后果？ 只有我自己，和有一千个用户，是两种完全不同的游戏。

四个问题里有三个指向「低风险」，那么放心地用 Vibe Coding 提速，它的价值是真实的：它把「从想法到能看到东西」的时间从半天压到十分钟，这个压缩本身就是巨大的生产力。

一旦有两个以上指向「高风险」，你就该把它降级成 AI 辅助编程：读代码、加测试、走评审。工具可以不变，但流程必须变。

结论：别争名词，标好风险

回到开头的问题：Vibe Coding 到底是什么？

笔者的判断是，它描述的不是某类工具，而是一种控制权与验证权的让渡程度。同样的模型、同样的 IDE，在不同的人手里可以是辅助编程，也可以是 Vibe Coding，区别只在于人是否还在做最终判断，以及是否有机器流程替人做判断。

所以团队内部真正需要统一的从来不是名词，而是标签体系：哪一类改动允许不读代码、哪一类必须读、哪一类必须有测试护栏。把这些边界写进规范，比争论「这算不算 Vibe Coding」有价值得多。
