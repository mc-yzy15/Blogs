Monorepo 包边界治理：依赖方向、公开 API 与循环依赖的工程约束

作成日2026-09-13|更新日2026-09-13|云计算

Monorepo 包边界治理：依赖方向、公开 API 与循环依赖的工程约束

把代码放进一个仓库不等于拥有了 monorepo 的收益。真正的收益来自「包」这个单位：独立的版本、独立的构建、独立的边界。如果边界可以随意穿透，monorepo 就退化成一个巨大的单包，只是多了一层目录。

边界的第一性问题：依赖方向

健康的依赖图是一张有向无环图，且方向单一。常见的分层是：

  • 基础设施层：类型、常量、工具函数，不依赖任何业务包
  • 领域层：领域模型与业务逻辑，只依赖基础设施层
  • 应用层：页面、路由、API 入口，依赖上面两层
  • 应用之间互不依赖

一旦出现反向依赖或同层互赖，任务图退化成链，缓存复用率骤降，语义也会混乱——比如工具包里开始出现业务判断。

判断一个包是否放错位置，有个简单测试：删掉它，其他包会不会因为缺少业务知识而无法编译？ 如果会，说明业务知识泄漏进了基础层。

公开 API 收敛：包只能从门口进出

边界不仅是「谁能依赖谁」，还包括「通过什么依赖」。常见问题是应用直接从 packages/ui/src/components/button/internal-impl.tsx 深链导入，绕过包的设计意图。

解决办法是强制入口收敛：

  • 每个包通过 exports 字段声明唯一入口
  • 禁止 @org/ui/src/* 这类深链
  • 内部文件放在约定目录（如 src/internal/），并用 lint 规则标记为私有

exports 一旦声明，Node 与现代打包器就会拒绝未列出的子路径，等于在运行时和构建期同时上了锁。这比只靠 code review 靠谱得多。

用自动化检查守住边界

人工守边界一定失守。可落地的检查有三类：

检查类型 工具方向 拦截时机 维护成本
依赖方向白名单 ESLint 规则 / dependency-cruiser 本地 + CI 低，规则集中维护
深链导入检测 ESLint no-restricted-imports 本地 + CI 低
循环依赖检测 madge / dependency-cruiser CI 门禁 中
包体积与产物审计 自定义脚本 CI 门禁 中
依赖声明一致性 syncpack / knip CI 门禁 中

经验上，前两类是必做的，投入很小但能挡住绝大多数越界。第三类在包数量超过 20 个后价值凸显。

循环依赖：为什么必须零容忍

循环依赖在单包里可能只是警告，在 monorepo 里后果被放大：

  1. 构建顺序无法确定，Turborepo 可能直接报错或行为不可预期
  2. 缓存键互相引用，任何一侧变动都使另一侧失效，缓存价值归零
  3. 拆包与发布时无法独立进行

打破循环的常见手法，按代价从低到高：

  1. 把共享类型抽到独立的 types 包（无运行时依赖，最安全）
  2. 用依赖注入替代直接引用，由应用层负责组装
  3. 定义接口包，双方依赖接口而非实现
  4. 重新划分领域，把一个包拆成两个方向严格单向的包

第 1 种在大多数场景下就够用了。类型包没有副作用，不参与构建产物，进图也不会引入运行时耦合。

取舍：包应该切多细

切得过粗，缓存粒度大、改动影响面广；切得过细，包数量膨胀、跨包跳转成本高、配置维护量上升。

笔者的经验阈值：

  • 少于 3 个使用者，先不单独建包
  • 一个包被改动后若影响超过一半的应用，考虑它是否过度通用
  • 单个包的源码超过约千行且职责不单一，考虑拆分
  • 包内出现两个以上明显独立的领域概念，应当拆

还有一个常被忽略的成本：每个包都要维护 package.json、tsconfig、构建配置、lint 配置。能用约定和共享配置消除的部分，尽量用 extends 复用，避免配置文件数量随包数线性膨胀。
