Turborepo 远程缓存落地的三个硬问题：隔离、命中率与命中失败

作成日2026-09-13|更新日2026-09-13|云计算
|閲覧数:

Turborepo 远程缓存落地的三个硬问题：隔离、命中率与命中失败

本地缓存只能加速你重复构建自己的分支。真正把 CI 时长压下来的是远程缓存：一个开发者或一条流水线算过的结果，整支团队都能复用。但远程缓存不是打开开关就完事，落地阶段总会撞上三个具体问题。

问题一：缓存隔离，别让 feature 分支污染主干

远程缓存默认按「哈希 → 产物」存储，键里不包含分支信息。这意味着如果 A 分支构建了一个哈希为 abc123 的产物，B 分支算出同样的哈希，就会直接复用 A 的产物。

正常情况下这是好事：内容相同，产物自然相同。风险出现在两类场景：

  • 产物含构建时环境差异：例如不同分支注入了不同的 API 地址，但环境变量没进 env 声明，哈希相同而产物应当不同。
  • 本地脏构建上传：开发者本地带着未提交改动构建并上传，恰好哈希与 CI 一致时，会把错误产物喂给流水线。

防护手段有三层：

  1. 把影响产物的所有环境变量写进 env / globalEnv，这是根本。
  2. 在 CI 上统一使用 --remote-cache-read-only 以外的写入策略，禁止非受信环境上传。
  3. 对关键应用开启签名校验（如 remoteCache.signature），防止缓存被篡改。

问题二：命中率为什么上不去

打开远程缓存后发现命中率只有个位数，通常不是缓存坏了，而是哈希输入被无意放大了。

常见诱因 现象 修复方向
未声明的环境变量 每次 CI 哈希都变 补进 env / globalEnv
时间戳或随机数写进产物 命中率恒为 0 让构建产物确定性化
outputs 写成 ** 或 dist 不带子路径 缓存体积巨大、上传慢 精确声明产物路径
lockfile 频繁变动 全局哈希变化 检查是否被无关依赖抖动
源码里引用绝对路径 本地与 CI 哈希不同 用相对路径与 rootDir 变量

一个实用技巧是用 --dry=json 或 --summarize 看每个任务的哈希输入，对比两次运行差异。

问题三：缓存命中却构建失败

这是最让人头疼的一类：日志显示 cache hit，但后续步骤缺文件或报错。绝大多数情况指向 outputs 与 inputs 声明不匹配。

Turborepo 的缓存只保存 outputs 里声明的东西。如果构建实际产出 dist/client、dist/server，而你只声明了 dist，恢复时不会丢文件（因为 dist 是前缀），但如果你声明了 dist 而实际产出在 .next，就会命中一个空缓存。

反向问题同样存在：inputs 没排除测试文件，导致改一个 .test.ts 就失效整条链。

.next/cache 本身是 Next.js 自己的增量缓存，放进 Turborepo 的 outputs 会让缓存包体积翻好几倍，收益却不明显，通常应排除。

自建缓存服务还是用托管方案

维度 Vercel 托管远程缓存 自建（S3 / Redis 后端）
接入成本 低，环境变量即用 需部署服务、配鉴权
跨团队共享 天然支持 需自行设计权限模型
数据合规 产物在第三方 完全自控
成本 随使用量与套餐计 存储与流量自付
可观测性 平台提供命中率指标 需自建监控

选择的核心不是价格，而是「产物是否包含敏感数据」。如果构建产物里含有服务端密钥或客户数据，自建更稳妥；纯前端静态资源放托管通常更省心。

维护远程缓存的三条日常纪律

  • 定期轮换缓存：schema 大改或依赖大版本升级后，主动失效一次，避免旧产物污染新结构。
  • 监控缓存体积增长：缓存只增不减会推高存储与恢复耗时，按周看增长曲线。
  • 把命中率当度量指标：在 CI 里记录 cache hit / miss 比例，命中率突然下跌通常是哈希抖动的早期信号。
