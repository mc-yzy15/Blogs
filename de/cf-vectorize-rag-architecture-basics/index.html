Cloudflare Vectorize 做 RAG 的完整架构：从索引构建到召回链路

把 RAG 拆开看，它其实只有两件事：把知识变成可检索的向量，以及把检索结果塞进模型的上下文。听起来简单，但真正落地时，绝大多数工程问题都出在”变成向量”和”塞进上下文”这两步之间的缝隙里。本文以 Cloudflare 的 Vectorize 为核心，讲清楚一条最小可用、又能持续演进的 RAG 链路。

为什么把 RAG 放在边缘而不是自建向量库

自建方案（例如外部托管的向量数据库 + 一台常年运行的 API 服务）的诱因是”可控”：参数可调、算子可换、索引结构任选。代价则是三件长期负担：运维、网络往返、以及向量库与业务服务之间的数据同步。

边缘栈的价值恰恰在于把这三件事一起消解：

  • 就近执行：Workers 在全球节点分布运行，检索与拼接 prompt 的往返不再是”用户 → 你的机房 → 用户”的跨洋链路。
  • 免运维：Vectorize 不暴露分片、副本、内存参数，把调优空间换成了确定性的运维成本。
  • 同栈数据：D1 存结构化元数据、R2 存原始文档、KV 存热配置、Vectorize 存向量，四者之间不需要自建同步管道。

反过来说，如果你的场景要求自定义量化、自定义距离度量、或者需要几十亿量级向量的单索引，边缘方案当前未必是首选。选型的前提是承认：RAG 的瓶颈通常不在检索算法，而在数据质量与请求链路。

一条最小可用的 RAG 链路

这条链路的每一个箭头，都是一次潜在的失败点。设计时要明确：哪一步失败可以降级，哪一步失败必须报错。 例如向量库暂时不可用时，可以降级成”只用关键词检索”；而 LLM 调用失败时，通常只能如实返回错误。

索引构建：切分策略比模型选型更重要

很多人把精力花在”选哪个 embedding 模型”上，但实践中影响召回质量最大的是切分。RAG 的检索单位是 chunk，chunk 的边界决定了语义是否完整。

几条经验法则：

  1. 按语义结构切，不按固定字数切。Markdown 按标题层级切、代码按函数切、FAQ 按问答对切，效果通常好于机械的 512 字符滑窗。
  2. 块间保留重叠。相邻块重叠约 10%~20% 的内容，可以缓解”答案跨边界”的丢失问题。
  3. 块要带元数据。每个块至少要记住：所属文档 id、章节路径、更新时间、权限标签。后两者在过滤与安全上几乎是必需的。
  4. 块不宜过碎。过小的块会让 topK 召回一堆碎片，反而稀释了上下文信噪比。

召回链路：topK、阈值与重排的取舍

检索质量由三个参数共同决定，它们彼此耦合：

参数 作用 调大 调小
topK 召回候选数量 召回更全，但噪声变多、token 成本上升 上下文干净，但可能漏掉关键块
score 阈值 过滤低相关结果 更严格，可能召回为空 更宽松，噪声增多
重排（rerank） 对候选二次排序 显著提升精度，增加一次模型调用 省成本，但排序粗糙

一个常见的误判是”topK 越大越好”。实际上当 topK 超过某个点后，新增的上下文带来的干扰会抵消召回收益，模型反而更容易被无关内容带偏。更稳妥的流水线是：先用较大的 topK 召回（例如 2030），再用 rerank 截断到 35 条送入 LLM。

重排这一步值得多花点预算，因为它是”检索”与”生成”之间的质量闸门。若不想引入额外模型，也可以用一个轻量的策略：按元数据（如章节权重、更新时间）做加权，或者对同一文档的碎片做合并去重。

与 D1 / R2 / Workers AI 的组合方式

四件套的职责边界建议这样划分：

  • R2：原始文档（PDF、Markdown、HTML）。它是唯一的事实源，任何时候都能重建向量。
  • Vectorize：向量与轻量 metadata。用于检索阶段定位 chunk。
  • D1：chunk 正文与结构化元数据。用于检索后取回内容，也用于管理后台做统计。
  • Workers AI：embedding 与生成模型。属于无状态计算，可替换。

这条分工的关键是：向量索引要能随时重建。如果你把原文只存在向量库里，一旦切分策略变更或模型升级，就没有办法无损重建。把 R2 当作事实源，Vectorize 当作可丢弃的派生视图，架构的演进成本会低一个量级。

何时该放弃边缘 RAG

不是所有场景都适合。以下情况建议重新评估：

  • 需要毫秒级返回且索引在十亿向量以上，边缘节点的冷启动与索引规模可能成为瓶颈。
  • 需要强一致的实时写入 + 复杂聚合查询（类似全文检索的布尔组合），关系型或专用检索引擎更合适。
  • 合规要求数据必须留在特定地域的单一数据中心内，全球分布反而是负担。
