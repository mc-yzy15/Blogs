边缘冷启动与调度：为什么”无服务器”也会慢

边缘平台常被描述为”冷启动几乎不存在”。对于平台自身的实例化而言，这句话大体成立；但对你的应用而言，冷启动依然存在，只是换了形态。很多团队上线后发现 P99 明显高于预期，最后定位下来既不是网络问题，也不是数据库问题，而是”某些请求恰好碰上了新实例”。

冷启动其实有两种

把两种混在一起讨论，是排障效率低下的主要原因。

第一类：平台冷启动（Infrastructure Cold Start）
指平台为了执行你的代码而创建隔离环境、初始化引擎上下文、加载你的脚本。在 Isolate 模型下，这一部分通常在毫秒量级到几十毫秒量级，比容器模型低一个数量级。

第二类：应用冷启动（Application Cold Start）
指你的代码在被执行前需要完成的初始化：解析大型配置、建立数据库连接、加载并编译体积庞大的依赖、初始化 SDK、拉取远端配置。这一部分完全由你控制，也常常是 P99 超支的真正来源。

一个实用的判断方法：如果空函数（只返回 "ok"）的 P99 很低，而你的业务函数 P99 高得多，那么问题在第二类。

调度是怎么决定”你会不会冷”的

平台需要为每个（或每组）请求找到可用的执行上下文。影响调度结果的常见因素：

  • 实例是否被回收：空闲一段时间后上下文被回收，下一个请求就要重建；
  • 并发压力：突发流量下同一上下文可能被多个请求复用，但也可能触发新建；
  • 地域分布：流量被 Anycast 分散到大量 PoP，每个 PoP 的请求频次可能都偏低，导致”到处都在冷启动”；
  • 部署与版本切换：每次发布都会让旧上下文失效，发布瞬间的请求更容易命中冷路径；
  • 代码体积：脚本越大，加载与初始化的绝对成本越高。

最后一条值得强调：边缘是”多地多次初始化”的环境。在传统服务器上，一次部署只初始化几次；在边缘上，同一个脚本会在许多地点被反复初始化。因此”体积与初始化开销”在边缘的权重，远比在单体服务中大。

一张表：延迟来源与可控性

延迟来源 典型量级感受 谁能优化 优化手段
客户端到 PoP 的网络 RTT 取决于距离与路径 有限 启用 HTTP/3、复用连接、减少跳数

业务逻辑与上游调用 取决于实现 你 缓存、并发化、减少串行依赖

优化顺序应当是从下往上：先把业务逻辑与上游调用做扎实，再处理初始化，最后才是纠结平台那几十毫秒。反过来做，收益会被上游的慢调用完全吞没。

度量：先能看见，再谈优化

没有度量就优化冷启动，等于闭着眼睛调参。最低限度的度量要求：

  1. 上报分布而不是均值：P50/P95/P99 分别看，冷启动天然是长尾现象，均值会把它抹平；
  2. 上报每请求的自定义耗时：把初始化耗时与业务耗时分开打点；
  3. 按 PoP 与版本拆分：低流量 PoP 与发布后的新版本，冷启动比例通常显著更高；
  4. 记录请求量极低的地区：这些地区每次请求都可能触发初始化。

把 x-init-ms 与 x-biz-ms 打到访问日志里，你会立刻看清两者数量级是否同一水平——这决定了优化方向。

优化清单：按投入产出排序

高收益、低风险

  1. 延迟初始化：把连接建立、配置读取挪到首次真正需要时执行；
  2. Promise 缓存：同一个实例内复用初始化 Promise，避免并发请求各自初始化；
  3. 精简依赖：检查打包体积，剔除只用一两个函数的巨型库；
  4. 避免内联大 JSON：几十 KB 的配置直接内联会拖慢脚本解析，考虑放到外部存储按需读取。

中收益、需要设计

  1. 减少串行上游调用：能并行的用 Promise.all 并行，串行是最常见的延迟放大器；
  2. 把强一致读改为可缓存读：结合缓存策略降低上游压力；
  3. 预热关键路径：对延迟极敏感的业务，可在部署后主动触发一轮请求，让主要 PoP 建立上下文。

需要谨慎评估

  1. 多区域冗余：提升可用性，但也会让”每处都初始化”的问题更分散，收益与成本要算清楚；
  2. 减少部署频率：发布越频繁，冷启动窗口越多；把多次小改动合并发布可减少抖动。

反直觉提醒：“提高并发”不总是减少冷启动。在某些负载形态下，突发并发会让平台创建更多上下文，短期内冷启动比例反而上升，直到上下文数量稳定下来。因此观察冷启动必须结合”发布事件”与”流量曲线”一起看。

一个常见误区：把冷启动当成网络问题

排障时最常见的一条弯路是：用户抱怨”第一次访问很慢”，团队立刻去查 DNS、TLS、CDN 缓存，最后发现是应用初始化写得太重。

避免这条弯路的方法是把时间轴拆开看：

  • 握手阶段（DNS + TCP/TLS）慢 → 网络与协议问题；
  • TTFB 之前的一段空白（首字节延迟高，但内部耗时低）→ 可能是上下文创建或排队；
  • 内部耗时高（x-init-ms 大）→ 应用初始化问题；
  • 内部业务耗时高（x-biz-ms 大）→ 上游依赖或业务逻辑问题。

这四个区间对应四种完全不同的修复动作。把它们混为一谈，就只能得到”边缘就是不稳定”这种没有行动价值的结论。

结语

边缘平台确实把平台侧冷启动压得很低，但这不意味着你的应用天然无冷启动。在边缘，实例化是高频事件、脚本会在多地反复初始化，因此初始化成本是常态开销的一部分。把它当作需要主动管理的指标，而不是偶发异常，是让边缘应用稳定达标的关键一步。
