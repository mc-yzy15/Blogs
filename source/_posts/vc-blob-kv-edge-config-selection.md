# Blob、KV 与 Edge Config 的选型对比：三种"边缘存储"到底该用在哪儿

很多团队在 Vercel 上做第一个"真正有状态"的功能时，都会遇到同一个困惑：Blob、KV、Edge Config 看起来都是"托管的存储服务"，都能在 Serverless 函数里 `import` 一下就用了，那为什么不干脆选一个用到底？

答案藏在它们的存储模型里。这三种服务在设计之初就对应了完全不同的数据形态和访问模式，如果混用，轻则成本翻倍，重则写出"看着能跑、上线就出错"的一致性问题。本文不罗列 API，而是从数据建模的角度把它们拆开讲清楚。

## 先分清三种数据形态

理解这三者的最快方式，是问自己一个问题：**你的数据是"文件"、"键值对"还是"配置"？**

- **Blob** 面向的是**对象**：图片、视频、PDF、用户上传的任意二进制文件。它的心智模型接近 S3 桶——写入后得到一个不可变的 URL，删除是显式的。
- **KV** 面向的是**可变的小值**：会话、计数器、限流状态、功能开关的运行时快照。它是 Redis 语义的托管子集，强调低延迟读写。
- **Edge Config** 面向的是**几乎不变的配置**：路由规则、A/B 实验分组表、上游服务地址名单、白名单。它的读延迟极低，但写入是"发布式"的，而不是"事务式"的。

把这三句话记住，后面所有的取舍推导都会自然很多。反过来说，绝大多数踩坑都可以归结为把配置塞进了 KV，或者把会话塞进了 Edge Config。

## Blob：为不可变对象而生的分发层

Blob 的核心设计取向是"写一次、读无数次"。当你通过 `put()` 上传一个文件时，系统返回的是带随机后缀的 URL，这个 URL 在对象被删除前保持稳定。

```ts
import { put, list, del } from '@vercel/blob';

// 上传：让服务端生成随机文件名，避免用户可控路径
const blob = await put(`uploads/${crypto.randomUUID()}.png`, file, {
  access: 'public',
  addRandomSuffix: true,
});

// 列举某个前缀下的对象
const { blobs } = await list({ prefix: 'uploads/' });

// 显式删除
await del(blob.url);
```

几个工程上必须注意的点：

1. **不要把用户输入直接拼进路径**。路径穿越和覆盖攻击在对象存储上同样成立，用 `crypto.randomUUID()` 生成文件名，原始文件名只存在数据库里。
2. **不要在上传路径里做鉴权之外的判断**。Blob 本身的访问控制粒度有限，敏感文件应该走私有访问 + 服务端签名。
3. **删除和列举是最终一致的**。刚 `del()` 掉的对象可能在 `list()` 里短暂出现，别把 `list()` 当数据库查询用。

Blob 的计费通常拆成三块：存储容量、读写操作次数、以及出网流量。前两者量级很小，真正贵的是**流量**。如果你的图片没有经过优化就直接分发原图，账单会以你意想不到的速度增长——务必配合 `next/image` 之类的优化层使用。

## KV：低延迟可变状态，但一致性有边界

KV 的价值在于延迟。把会话或限流计数放在 KV 里，函数在冷启动之后的读取通常是个位数毫秒级的，这对边缘运行时尤其重要——你不可能为了读一个 session 去跨区域回源到某个单区域数据库。

```ts
import { kv } from '@vercel/kv';

export async function rateLimit(ip: string, limit = 60) {
  const key = `rl:${ip}`;
  // 原子的自增 + 过期，避免"读-判断-写"的竞态
  const count = await kv.incr(key);
  if (count === 1) {
    await kv.expire(key, 60);
  }
  return count <= limit;
}
```

上面这段代码的写法很关键：**用 `INCR` 而不是 `GET` 再 `SET`**。后者看起来更直观，但在并发场景下会丢计数，这是限流最经典的 bug。

KV 的一致性模型需要特别说明。它是**最终一致**的：一次写操作在源区域确认之后，其他边缘节点的读取可能会有短暂的陈旧窗口。这个窗口通常是毫秒到秒的量级，具体以实现和官方文档为准。由此推导出两条实践规则：

- **不要用 KV 做需要读己之写（read-your-writes）的场景**。用户刚提交的表单立刻在同一次交互里查，可能查不到。
- **不要在 KV 上做需要跨键原子性的业务**。虽然没有事务，但单键的 `INCR`、`SETNX` 这类操作是原子的，够用的场景其实很多——关键是设计时别指望多键一致。

## Edge Config：读得极快，但写入是一等公民之外的少数派

Edge Config 的定位非常明确：**极小、极少变、读极多**的数据。它的读取被内联到边缘网络的配置分发路径上，延迟可以低到几乎没有网络往返的感觉——通常在个位数毫秒甚至更低，具体以官方文档为准。

典型场景是功能开关和实验分组：

```ts
import { createClient } from '@vercel/edge-config';

const edgeConfig = createClient(process.env.EDGE_CONFIG);

export async function middleware(req: Request) {
  const flags = await edgeConfig.get<Record<string, boolean>>('flags');
  if (flags?.newCheckout) {
    return new Response('checkout-v2');
  }
  return new Response('checkout-v1');
}
```

但请注意它的三个硬约束，这些往往是踩坑的根源：

| 维度 | Edge Config | KV | Blob |
|---|---|---|---|
| 数据形态 | 小型配置项 | 键值对 / 计数器 | 二进制对象 |
| 单值大小上限 | 很小（KB 量级） | 较大（MB 量级） | 很大（GB 量级） |
| 读延迟 | 极低 | 低 | 一次 HTTPS 往返 |
| 写延迟 | 秒级生效 | 毫秒级 | 立即 |
| 一致性 | 发布式，有传播延迟 | 最终一致 | 强一致（单对象） |
| 适用写入频率 | 每天几次 | 每秒数千次 | 任意 |
| 典型用途 | 功能开关、路由表 | 会话、限流 | 图片、附件 |

Edge Config 的写操作不是"改一个值"这么轻，它更像一次**配置发布**。如果你打算每秒写十几次，选错服务了——那是 KV 的活。反过来说，如果你的功能开关几秒钟才生效，业务上完全无感，但换来了中间件里几乎零成本的读取，这个交换非常划算。

## 决策路径：从数据特征反推服务

与其记服务名，不如记住这条判断链：

1. **是二进制文件吗？** 是 → Blob。文件大小、是否公开、是否需要 CDN 缓存决定了你的访问模式。
2. **是可变的运行时状态吗？** 是 → KV。但要确认你能接受最终一致，并且不需要跨键事务。
3. **是全局共享、变化极少的读重度数据吗？** 是 → Edge Config。
4. **以上都不是？** 那么你大概率需要的是一个真正的数据库（Postgres / SQLite 等），而不是这三者中的任何一个。

第 4 条值得单独强调。很多团队用 KV 硬扛关系型数据，用 `SCAN` 模拟查询，最后在数据量上来之后陷入困境。这三者是**补充层**，不是数据库的替代品。

> **经验法则：** 把 Blob 当"文件柜"、KV 当"便签纸"、Edge Config 当"公告板"。便签纸可以随时撕掉重写，公告板贴上去要等一会儿大家才看到，而文件柜里的东西一旦放进去了就最好别乱动。

## 组合使用才是常态

真实的架构几乎从不会只用一种。一个典型的电商站点可能是这样分工的：

- 商品图与用户头像 → **Blob**
- 购物车与会话 → **KV**
- 灰度开关与推荐算法参数 → **Edge Config**
- 订单与库存 → **托管 Postgres**

关键在于让每一层承担它最擅长的事，并明确它在一致性上的承诺。当你在设计评审里被问到"这个数据为什么放在 KV 而不是 Edge Config"时，你能答出"因为它每秒写几十次，且需要毫秒级读己之写"，那这次选型就是站得住的。

反过来，如果答案是"因为当时 KV 先建好了"，那就值得在下一个迭代里重新审视一遍。存储选型的成本，往往不在于第一次写代码，而在于三年后你想改的时候发现到处都在依赖那个错误的一致性假设。
