# 边缘网络的解剖学：一次请求如何穿过 Cloudflare 的全球拓扑

很多人对"边缘"的理解停留在"机房多、离用户近"。这个理解不算错，但远远不够。真正决定边缘平台行为特征的，不是机房数量，而是**路由决策发生在哪一层、由谁做出、依据什么信息**。本文沿一次 HTTPS 请求的路径往下走，把 Cloudflare 的全球网络拆成可分析的几层。

## 第一层：Anycast 与"同一 IP 出现在几百个地方"

传统托管的做法是把域名解析到一个固定 IP，用户流量汇聚到某几个入口。边缘网络的做法完全不同：同一个 IP 地址段在全球大量 PoP（Point of Presence）同时对外宣告。这就是 Anycast。

关键在于，Anycast 不提供一个"最近"的答案，它提供一个"由 BGP 决定"的答案。用户方的路由器选择哪条路径，取决于它自己收到的路由表、本地策略、对等互联关系与运营商偏好，而不是地理距离。这带来两个直接后果：

- **收敛快、抗打击**：某个 PoP 或某段链路出问题，BGP 撤销宣告后流量会自动绕行，不需要改 DNS，也不需要客户端重试逻辑。
- **不可预测**：同一城市的两家运营商用户，可能被路由到相隔上千公里的两个不同 PoP。你无法通过"我在上海，所以我在上海边缘执行"来做业务假设。

> 经验法则：**不要根据客户端地理位置写业务逻辑**。如果业务必须区分区域，使用平台提供的区域属性（如 `request.cf.colo`、`request.cf.country`），而不要自己维护 IP 段到区域的映射表——那张表一定会在某次互联调整后失效。

## 第二层：进入 PoP 之后的协议终止

流量抵达 PoP 后，边缘必须在尽可能早的位置完成 TLS 终止。原因很实在：只有解密之后，平台才能看到 HTTP 层信息（Host、Path、Header），才能做出"这个请求该由谁处理"的决策。

这一层通常是这样的顺序：

1. TCP/UDP 连接建立（TLS 1.3 支持 0-RTT 恢复，可显著降低再次访问的握手开销）；
2. TLS 握手与证书选择，基于 SNI 匹配到对应域名的证书；
3. HTTP 解析与规范化（去重路径、处理编码、补齐 Header）；
4. 规则匹配：缓存规则、WAF 规则、重写规则、限流策略依次求值；
5. 决定是命中缓存直接返回，还是进入计算层（Workers / 回源）。

注意第 4 步的隐含语义：**防火墙与缓存判定通常发生在计算之前**。这意味着如果你的 Worker 承担了全部业务逻辑，那么 WAF 拦截的请求根本不会进入你的代码——这既是性能优势，也是排障时容易踩的坑：日志里看不到请求，不代表请求不存在。

## 第三层：计算层的调度与隔离

当请求被判定需要执行代码，平台需要在 PoP 内找到或创建一个运行环境。这里有两个层次的调度：

**宏观调度**：选哪个 PoP 执行。平台可能出于负载、容量、合规（例如数据驻留要求）做出与 Anycast 首次抵达点不同的选择。

**微观调度**：在 PoP 内选哪台机器、哪个进程承载这段代码。这一层直接决定冷启动表现。

隔离模型上，主流边缘平台走的是 V8 Isolate 路线：同一个进程内用多个 Isolate 承载不同租户的代码，共享进程资源但内存与执行上下文互相隔离。这与"一容器一实例"的模型在启动成本上有数量级差异。后续会有专门一篇展开对比，此处只强调一个推论：

**因为实例化成本极低，边缘平台倾向于"每请求或每次突发都新建上下文"，而不是像传统容器那样长期保活。** 这决定了你必须把初始化成本视为常态开销的一部分，而不是只在服务重启时发生一次。

## 一张表：各层决策与可观测性

| 网络层 | 主要决策者 | 决策依据 | 你能观测到什么 |
|---|---|---|---|
| BGP / Anycast | 运营商与骨干网 | 路由表、对等策略 | 几乎不可观测，只能通过 `colo` 间接感知 |
| TLS 终止 | 边缘平台 | SNI、证书覆盖范围 | 握手失败率、TLS 版本分布 |
| 规则引擎 | 边缘平台配置 | 路径、Header、IP 信誉 | WAF 事件、缓存命中率 |
| 计算调度 | 边缘平台运行时 | 负载、亲和性、容量 | 冷启动比例、执行时长 |
| 用户代码 | 你 | 你的业务逻辑 | 日志、Trace、自定义指标 |

这张表最重要的用途是**排障定位**：当"请求变慢"时，先确定问题落在哪一行，再决定是改配置、改路由、还是改代码。把四行混在一起讨论，只会得到"据说边缘很快，但我的应用很慢"这类无效结论。

## 一段代码：观察请求实际落到了哪里

边缘平台通常会在请求对象上注入网络元数据。下面是一个最小示例，用来确认请求的真实归属，而不是依赖猜测：

```js
export default {
  async fetch(request) {
    const cf = request.cf || {};
    const headers = new Headers({
      "content-type": "application/json; charset=utf-8",
      "cache-control": "no-store"
    });
    const body = JSON.stringify({
      colo: cf.colo,                 // 实际执行的边缘节点代码
      country: cf.country,           // 客户端国家/地区
      city: cf.city,                 // 客户端城市（粒度有限）
      asn: cf.asn,                   // 客户端运营商 ASN
      tlsVersion: cf.tlsVersion,     // 协商到的 TLS 版本
      httpProtocol: cf.httpProtocol  // HTTP/1.1 或 HTTP/2/3
    }, null, 2);
    return new Response(body, { headers });
  }
};
```

把这段代码部署到测试域名，从不同网络、不同地区访问，你会得到一组相当反直觉的结果：同一个办公室的 WiFi 与手机蜂窝网络，`colo` 可能完全不同。这正是 Anycast 的现实面貌。

## 为什么"靠近用户"常常不等于"更快"

边缘网络的收益不是免费的，它通过三种方式被抵消或反转：

- **回源放大**：如果每个边缘节点都独立回源，源站承受的连接数会随 PoP 数量近似线性上升。没有共享缓存或合并回源策略时，边缘反而让源站更容易过载。
- **一致性开销**：靠近用户的读很快，但如果每次读都要去远端确认最新值，节省下来的 RTT 会被一致性的等待吃掉。
- **状态分散**：无状态请求享受最优路径；一旦需要会话粘性或强一致存储，请求可能被迫"绕远路"。

因此正确的提问方式不是"边缘是否更快"，而是"**这个负载形态下，边缘把哪一段延迟变成了可消除的部分**"。静态资源、个性化拼装、鉴权前置、地理路由，这四类收益最确定；而需要频繁跨区域强一致写入的事务型负载，收益往往被抵消。

## 结语：把边缘当作有策略的网络来设计

理解拓扑层的最大价值，是让你在设计阶段就避开三类错误假设：假设位置稳定、假设路径唯一、假设请求一定被你的代码看见。把这三条从脑中去掉，你会发现边缘平台上那些"奇怪的限制"（无状态倾向、存储模型特殊、连接数受限）其实都是这套拓扑的合理产物。
