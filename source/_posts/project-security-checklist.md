# 上线前必做：我的个人项目安全体检清单

> 前阵子我给自己所有对外开放的项目做了一次系统性的安全审查。说实话，过程相当丢人——**我以为我写得挺安全的，结果查出一串「低级但致命」的问题**：有接口裸奔在公网、有密钥可能进过日志、有出站请求能打到内网地址。这篇文章不是安全专家的说教，是一个普通开发者「被自己吓到之后」整理出的自查清单。所有面向公网、接收外部输入的项目，都建议在上线前照着过一遍。

## 为什么要做这件事：一次真实的惊吓

事情起因很偶然。一个朋友半开玩笑地说要帮我「测试」一下接口，结果他花了不到半小时就找到两个问题：一个是某个调试接口居然不需要鉴权就能访问内部数据，另一个是某个功能存在被用来探测内网的风险。

那天晚上我把所有项目都翻出来复查，越查越心虚。最让我后怕的不是技术有多难，而是——**这些问题全都不是「高深的漏洞」，而是「基本的卫生问题」。** 写代码时只要多想一步就能避免，而我当时就是没多想那一步。

所以这篇清单的定位很清楚：**不是让你成为安全专家，而是帮你把最基本的地基打牢。** 地基不牢，上面盖多漂亮的楼都是白搭。

## 体检第一项：密钥和配置

这是最基础、也最容易被忽视的一项。检查要点：

- **密钥绝不硬编码在代码里**，也不提交进 git。放在环境变量或专门的密钥管理服务里。
- **环境变量缺失时要快速失败**，而不是默默用默认值顶上。一个「方便开发」的默认密码，上线后往往会变成真实漏洞。
- **数据库里不存密钥明文**。API key、访问令牌这类敏感字段，只存哈希值，创建时只展示一次。
- **日志里不出现密钥和敏感信息**。排查历史日志前，先确认日志组件做过脱敏。
- **被泄露的密钥要有吊销机制**，而不是只能「整把推倒重来」。

我的血泪教训是：曾经图省事把某个服务的 key 写死在配置文件里，还顺手提交到了仓库。虽然仓库是私有的，但「私有」不等于「安全」——只要有一天仓库被分享、被克隆、被备份外泄，key 就全完了。

## 体检第二项：鉴权与授权

鉴权和授权是两件事：**鉴权是「你是谁」，授权是「你能干什么」。** 很多项目只做了前者，忘了后者。

- **每个非公开接口都必须校验身份**，不能有「内部接口不需要鉴权」的侥幸。
- **校验身份之后还要校验归属**：用户 A 能不能访问用户 B 的数据？很多「越权漏洞」（IDOR）就是这么来的——登录了就能访问，但访问的是不该访问的资源。
- **会话和令牌要用安全的方式管理**：Cookie 加 HttpOnly，令牌别放在 URL 查询参数里（会进日志和历史记录），过期时间要合理。
- **密码存储用慢哈希**（bcrypt / argon2 / scrypt），不要用 MD5、SHA-1 这种快速哈希，更不要存明文。
- **管理功能要和普通用户功能隔离**，管理端点用独立的管理员鉴权。

判断标准很简单：**把你自己当成一个「刚注册的普通用户」，试一遍能不能通过改 ID、改参数访问到别人的数据。** 能访问到，就是洞。

## 体检第三项：注入类问题

SQL 注入、命令注入、路径穿越，这几兄弟每年都还在排行榜上，说明它们远没有绝迹。

- **SQL：永远参数化查询**，任何用户输入都不能拼进 SQL 字符串。需要动态排序、动态表名时，字段名走白名单，而不是直接拼用户输入。
- **命令执行：永远不要用 shell 字符串拼接用户输入。** 需要执行命令时用参数数组形式（`subprocess.run([cmd, arg])` 这种），并且对输入里的 shell 元字符（`` ` ``、`$`、`;`、`|`、`&` 等）保持警惕。
- **路径处理：用路径库拼接并做规范化**，然后校验结果确实在允许的基目录内。文件名里出现 `..`、`/`、`\`、盘符、空字符的，一律拒绝。
- **反序列化：不要对不可信输入用 picke、unserialize 这类机制**，优先用 JSON 配合具体的数据结构（DTO）做校验，别一把梭反序列化成裸对象。

这几类问题的共同点是：**出问题的地方都不是「看起来很危险」的地方，而是「看起来只是处理了一下输入」的地方。** 所以原则只有一个——所有外部输入，默认都是恶意的。

## 体检第四项：出站请求与 SSRF

这个坑我前阵子刚踩过，专门拎出来说。如果你的服务器需要根据用户提供的 URL 去发请求（比如「导入链接」「抓取网页」「代理转发」），就要警惕 **SSRF（服务端请求伪造）**：攻击者可以让你的服务器去访问它本不该访问的地方——内网服务、云元数据接口（那里可能躺着你的云凭证）。

防护要点：

1. **协议白名单**：只允许 `http` / `https`，其他协议一律拒绝。
2. **目标校验**：解析出 host 后，拒绝内网 IP、保留地址和云元数据地址（如 `169.254.169.254`）。
3. **别盲目跟随重定向**：重定向可能把你带到校验时没见过的地址，需要手动逐跳校验。
4. **别让用户直接指定任意内网地址**：能用白名单/固定前缀解决的，别给用户完整的 URL 自由度。

顺带一提：DNS 重绑定是个高级玩法，但对我们这种体量的项目，先把上面四条做了，就已经挡掉 99% 的脚本小子了。

## 体检第五项：Web 行为

如果你的项目是 Web 服务，下面几项也建议过一遍：

- **CORS 别开成 `*` + 带凭证**。正确姿势是：凭证请求只允许明确白名单的源，普通公开接口可以宽松些，但别一刀切。
- **响应头补齐**：`X-Content-Type-Options: nosniff`、`Content-Security-Policy`、`Referrer-Policy` 这几个基础头，加上几乎零成本，能挡掉不少浏览器端的低级问题。
- **输出编码别裸奔**：渲染用户内容时用框架自带的自动转义；确实需要输出 HTML 片段时，服务端做白名单清洗（类似 DOMPurify 的思路），别信前端。
- **重定向目标做校验**：只允许跳转到同源地址或预先白名单的域名，防止开放重定向被用来钓鱼。
- **上传功能**：后缀白名单 + MIME/文件头校验 + 大小限制 + 服务端重命名为随机 UUID + 存储目录不可执行。六条缺一不可。

## 体检第六项：日志与错误处理

这条最反直觉，也最容易被忽略：

- **返回给用户的错误信息要「笼统」**：登录失败就说「用户名或密码错误」，别告诉攻击者「用户名存在」。
- **详细信息（堆栈、SQL、内部路径）只进服务端日志**，永远不返回给客户端。
- **日志里不记录敏感数据**：密码、令牌、完整身份证号这类，一概不落盘；真需要排查时，记录脱敏后的片段。
- **给日志和监控留好告警**：被暴力破解、被刷接口、异常错误率飙升，这些「无聊但重要」的信号，能让你在出事当天发现，而不是事后再翻。

## 一份可以直接照做的检查清单

把上面所有内容压缩成一张表，建议你上线前逐项打勾：

| 检查项 | 关键动作 | 通过标准 |
|---|---|---|
| 密钥管理 | 环境变量 + fail-fast | 无硬编码、无默认密码、无明文入库 |
| 日志脱敏 | 日志组件过滤敏感字段 | 日志里搜不到任何 key/密码 |
| 身份鉴权 | 每个非公开端点校验身份 | 匿名请求全部被拒 |
| 越权防护 | 校验资源归属 | 换 ID/参数访问不到他人数据 |
| 密码存储 | bcrypt/argon2 等慢哈希 | 库中没有明文/弱哈希 |
| SQL/命令注入 | 参数化 + argv 执行 | 所有动态片段走白名单 |
| 路径穿越 | path 库规范化 + 边界校验 | 构造 `../` 无法逃出目录 |
| SSRF | 协议/IP 白名单 + 禁自动跳转 | 服务器无法访问内网/云元数据 |
| CORS | 白名单源 + 凭证分离 | 无 `*` + 凭证组合 |
| 安全响应头 | CSP/nosniff/Referrer-Policy | 头部均已配置 |
| 上传 | 后缀+MIME+重命名+不可执行目录 | 无法上传并执行脚本 |
| 错误信息 | 对外笼统、对内详细 | 客户端看不到堆栈/SQL |
| 管理端点 | 独立管理鉴权 | 管理接口不混用用户体系 |

## 写在最后

做完这次体检，我最深的感受是：**大多数安全问题不是「技术难度」问题，而是「有没有想过」的问题。** 攻击者不需要多高的水平，只需要比你的防线多想一步；而我们要做的，就是别让自己成为那个「一步都没多想」的人。

安全没有一劳永逸。代码在演进，依赖在更新，攻击手法在翻新，所以这份清单的价值不在「做一次」，而在「每次上线前都过一遍」。我现在的习惯是：**任何对外项目发布前，把这张表打印出来（或开个标签页），一项一项过，过完再上线。** 花不了半小时，但能省掉很多个不眠夜。

如果看完这篇你想给自己的项目也做一次体检——那就对了。去做吧，趁还没出事。
