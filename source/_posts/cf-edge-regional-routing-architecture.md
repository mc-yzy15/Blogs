# 在边缘做区域化路由：数据驻留与合规的架构落地

边缘平台的默认行为是"就近执行"，这对性能有利，但在合规面前可能直接违规：用户的个人信息被路由到境外节点处理，就可能触碰数据出境限制。**区域化路由要做的事，是在享受边缘性能的同时，把执行位置收进允许的范围内。**

## 合规需求如何翻译成技术约束

合规语言（"数据应当存储在境内""应当在授权区域内处理"）需要先被翻译成工程约束，否则无法设计。常见的三种翻译：

1. **存储约束**：数据只能写入指定区域的存储；
2. **计算约束**：处理数据的代码只能在指定区域执行；
3. **传输约束**：数据不得经由未授权区域中转。

三者的实现难度依次上升。存储约束最容易（选对存储区域即可）；计算约束要求平台支持区域限定执行；传输约束最难，需要审计整条链路，包括日志、监控、分析等"看不见的旁路"。

一个经常被忽略的点：**日志与分析链路也属于数据传输**。很多人只检查了主链路，结果请求头里的用户信息被送到了境外的日志平台，合规审计时才发现。

> 提醒：在设计阶段就把"所有数据流向"画成一张图，包括主链路、日志、追踪、监控、备份、异步任务。合规问题几乎总是出现在旁路上。

## 区域约束的三种表达方式

在边缘平台上表达区域约束，通常有以下几种手段：

**方式一：基于平台区域属性的请求级路由**
请求对象上通常会有区域信息（如执行节点代码 `colo`、国家/地区代码）。你可以在 Worker 入口做判断，决定是本地处理还是转发到特定区域的端点。

**方式二：运行位置约束（Run anywhere / 特定区域）**
部分平台提供显式的执行位置约束能力，让这段代码只能在指定区域内被调度。这比"在代码里判断再转发"更彻底，因为它消除了"代码已经先在不该去的地方执行过"的可能。

**方式三：存储侧约束**
无论计算在哪，写数据时明确指定区域。这通常通过使用区域化的存储资源来实现。

三种方式中最容易被忽略的是**方式二与方式一的差别**。只用方式一时，代码已经在边缘执行过了（可能已经读取了请求体），才决定转发——对于严格合规场景，这可能已经构成"在未授权区域处理数据"。因此**合规场景应优先使用平台提供的执行位置约束，而不是靠代码自行判断**。

```js
// 方式一示意：在入口做区域判断后转发
// 注意：此写法下代码已在当前 PoP 执行过，严格合规场景请改用平台级执行位置约束
const ALLOWED_COLOS = new Set(["SJC", "LAX", "IAD"]);

export default {
  async fetch(request, env) {
    const colo = (request.cf && request.cf.colo) || "UNKNOWN";

    if (!ALLOWED_COLOS.has(colo)) {
      // 转发到授权区域的处理端点
      const url = new URL(request.url);
      url.hostname = env.REGIONAL_ENDPOINT_HOST;
      // 保留原始路径与查询，避免语义变化
      return fetch(new Request(url, request));
    }

    return handleLocally(request, env);
  }
};
```

## 一张表：区域路由策略与代价

| 策略 | 实现层级 | 合规强度 | 性能代价 | 复杂度 |
|---|---|---|---|---|
| 全区域执行 + 区域化存储 | 存储 | 中 | 低 | 低 |
| 请求级判断 + 转发 | 应用 | 中低 | 中（多一跳） | 中 |
| 平台级执行位置约束 | 平台 | 高 | 低（原生调度） | 中 |
| 独立多区域部署 + 独立域名 | 部署 | 高 | 低 | 高 |

第四行值得说明：有些团队干脆为每个区域部署一套独立的应用与域名，用 DNS 或入口规则分流。这种方式合规最清晰（物理隔离），代价是运维复杂度与成本大幅上升，且跨区域的能力无法共享。

选择建议：**合规等级决定下限，性能与运维成本决定上限**。不要为了"看起来合规"而选择最复杂方案，也不要为了省事而用"代码判断"来应对严格审计。

## 失败与降级：区域受限之后没有"全自动绕行"

这是最容易踩的坑。普通的多区域部署可以做到"某个区域挂了，流量切到另一个区域"；但**区域受限的场景下，这个动作本身可能违规**。

因此降级策略必须提前设计，且必须是"合规的降级"：

1. **同区域内多可用区冗余**：在允许的区域内部做冗余，这是首选的降级维度；
2. **降级到只读或静态响应**：当期望区域不可用时，返回缓存内容或只读页面，而不是把请求转发到境外；
3. **明确拒绝并给出可解释错误**：合规不可用时，"拒绝服务"有时是正确行为，但必须让用户与监控都清楚原因，而不是表现为超时；
4. **人工开关**：对跨区域转发保留人工控制的开关，并记录每次开启的审计日志。

> 关键原则：**不要把"可用性优先"的默认习惯套到区域受限系统上**。在这类系统里，正确性（合规）优先级高于可用性，降级设计必须体现这一点。

## 可观测性：如何证明"数据没有跑到不该去的地方"

合规审计问的不是"你认为会不会",而是"你怎么证明"。因此需要可观测性设计：

- 每个请求记录**执行位置标识**，形成可导出的审计数据；
- 每个出站调用记录**目标区域**，尤其是存储与日志写入；
- 对**跨区域转发事件**单独计数并告警；
- 保留**配置变更历史**（区域白名单的每次修改）。

# 概念性查询示意：按执行位置统计请求量，用于审计留档
# 使用平台的日志分析能力（语法依平台而异，以官方文档为准）

## 团队落地：把合规约束写进工程流程

技术方案之外，真正让区域化路由可靠的是流程：

1. **架构评审清单加一条**：新增依赖时评估其数据区域；
2. **CI 校验**：在部署流水线里校验区域白名单配置是否被意外清空；
3. **变更审批**：跨区域转发的开启属于需要审批的变更；
4. **定期演练**：模拟某区域不可用，验证降级路径真的可用；
5. **文档化**：把"哪些数据在哪些区域"写成一张每个人都看得懂的图。

> 经验法则：**合规约束如果不能被自动化校验，就会在下一次紧急发布时被破坏**。把它变成流水线里的一个红灯，是最省事的长期方案。

## 结语

区域化路由的本质是**用性能与运维复杂度换取合规确定性**。它不是加几行判断的事，而是要在部署模型、降级策略、可观测性与流程上都做出配套调整。好消息是这些调整大多是"一次性投入、长期受益"——一旦建立，后续新增业务可以复用同一套约束与审计手段。
