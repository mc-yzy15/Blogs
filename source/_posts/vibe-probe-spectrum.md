# 从自动补全到意图编程：Vibe Coding 的光谱与能力分层

在上一篇文章里，我们把 Vibe Coding 从「AI 辅助编程」「低代码」「提示词生成应用」这几个概念里切了出来。但切开之后还有一件事没做：**Vibe Coding 自己内部也不是一个东西。**

让模型补全一行 if 判断，和让一个 agent 自己读仓库、改五个文件、跑测试、失败了自己重试——这两件事的差别，比「Vibe Coding 和低代码的差别」还要大。把它们统称为「用 AI 写代码」，就等于把自行车和货轮统称为「交通工具」。

这篇文章试图建立一个可用的分层模型。它不追求术语精确，追求的是**让团队在讨论工具选型时，能指着某一层说「我们要的是这个，不是那个」。**

## 两条轴：控制权与验证强度，以及由此得出的五个层级

分层之前先确定坐标。观察大量实际工作流后，笔者发现区分度最高的两个变量是：

- **控制权（Control）**：在一轮修改中，谁决定「改哪里、改成什么」。人逐步确认是最保守的一端，模型自主决策是另一端。
- **验证强度（Verification）**：改动是否被自动化手段拦截。没有检查是最弱的一端，编译器 + 类型系统 + 测试 + 静态分析全绿是最强的一端。

关键在于，**这两条轴是独立的**。很多人以为「模型越自主，验证必然越弱」，其实不然：一个被约束在「改完必须让 pnpm test 通过、否则回滚」循环里的 agent，其验证强度远高于一个人肉复制粘贴模型输出、然后直接 git commit 的开发者。

反过来也成立：人手动改一行代码，验证强度也可能是零。控制权和验证强度是两个旋钮，可以分开拧。

理解了这一点，就能避免一个常见错误——用「谁写的代码」来判断风险。风险取决于验证，不取决于作者是人还是模型。

把它们组合起来，就得到下面这个按控制权从人到模型、验证强度从弱到强综合排序的分层，每一层都对应一种已经被广泛使用的交互形态。

| 层级 | 名称 | 典型交互 | 控制权 | 验证强度 | 人的核心动作 |
|---|---|---|---|---|---|
| L0 | 自动补全 | 行内 Tab 接受/拒绝 | 人 | 沿用原流程 | 判断这行对不对 |
| L1 | 对话式生成 | 选中代码，让模型改写，人工应用 | 人 | 沿用原流程 | 审查 diff |
| L2 | 带护栏的生成 | 模型改代码，自动跑 lint/测试，失败回灌 | 混合 | 中到强 | 定义护栏、看结果 |
| L3 | 任务级 Agent | 给一个任务，agent 自行多文件修改并验证 | 模型 | 强（依赖护栏） | 写任务描述、验收益 |
| L4 | 意图编程 | 描述目标，系统持续演化产物并自证 | 模型 | 取决于系统设计 | 定义目标与验收标准 |

需要强调：**层级越高不代表越先进，只代表让渡的控制权越多。** L4 不是 L0 的进化终点，它们是不同工具，服务不同问题。

## L0-L1：把机械劳动还给人脑之外

L0 和 L1 是当今覆盖人数最多的两层，也是最没有争议的两层。

L0 的形态是补全。它的价值不在「生成得多聪明」，而在**摩擦极低**：一次按键，一个 Tab，接受或忽略，全程不打断思考。这一层的正确使用方式是「把它当成一个打字速度更快的自己」，而不是「当成一个会思考的同事」。

L1 的形态是对话式改写：选中一段代码，说「把这个回调改成 async/await，顺便处理错误」，然后审查 diff。这一层已经能显著改变工作节奏，因为它处理的是**有语义的整块逻辑**。但它的关键约束没变：**人必须读 diff**。跳过 diff 的人，其实已经越级到了 L2 的风险区间，却还在享受 L1 的心理安全感。

```bash
# L1 使用者的典型日常——改完立刻看 diff，再看类型检查
git diff --stat
git diff -- src/services/payment.ts
pnpm tsc --noEmit          # 类型是第一道最便宜的护栏
pnpm test -- --changed     # 只跑受影响的测试
```

这两层的隐性成本很低，唯一需要注意的是**注意力债务**：当补全过于流畅，人会逐渐降低审阅标准，把「看起来对」当成「是对的」。对抗手段很简单——把检查交给命令，而不是交给眼睛。

## L2：真正开始有价值的分水岭

L2 是笔者认为当前性价比最高的一层，也是被讨论得最少的一层。

它的定义是：模型直接修改工作区文件，但每一次修改后系统自动执行一组检查，检查结果被回灌给模型，模型据此修正，直到通过或者超出重试上限。人做的事从「读每一行代码」变成「定义护栏 + 判断业务语义」。

这一层的价值来自一个被低估的事实：**大部分 AI 生成的代码缺陷是机械性的、可被机器发现的**。类型不匹配、未处理的 Promise、导入路径错误、格式违规——这些占失败原因的绝大多数，而它们全都能被现有工具零成本捕获。一旦把这些交给自动循环，人就只剩下真需要人判断的部分：这个逻辑符合业务吗？这个抽象合理吗？

一个最小可用的护栏脚本大致长这样：

```js
// package.json 中的检查聚合脚本（示意，命令名以本地配置为准）
const checks = [
  ['typecheck', 'tsc --noEmit'],
  ['lint', 'eslint . --max-warnings=0'],
  ['test', 'vitest run --changed'],
];

for (const [name, cmd] of checks) {
  const r = run(cmd);
  if (r.code !== 0) {
    console.error(`[gate:${name}] failed\n${r.stdout}`);
    process.exit(1); // 交给循环，而不是交给人
  }
}
```

L2 的升级条件是**你真的配置了护栏**。没有护栏的 L2 会退化成「模型自动改一堆文件，人一脸茫然地 review 五百行 diff」——那比 L1 更差，因为决策颗粒度变粗了。

## L3：任务级 Agent 的收益与陷阱

L3 是近两年变化最快的层。交互形态从「改这段代码」变成「把这个需求做掉」：agent 自行搜索相关文件、规划修改、执行、验证、必要时回滚，结束时交付一个可评审的变更集。

它真正的收益不在速度，而在**并行度**。一个人可以同时推进多个 L3 任务，只要这些任务的边界清晰、文件不重叠。这让「一个人做一个小团队的事」第一次变得在工程上说得通，而不只是营销话术。

它的陷阱也集中在三处：

- **任务描述质量决定一切**。L3 不是「随便说说」，好的任务描述包含目标、边界、验收标准、禁止事项，写起来接近写一份小型的 RFC。很多人抱怨 agent 不靠谱，其实是任务描述只有一句话。
- **上下文污染**。agent 读到的旧代码、过期的注释、废弃的模块，会直接影响它的方案选择。仓库越混乱，L3 产出越随机。
- **错误的自信**。agent 在无法完成任务时，倾向于交付一个「看起来完成」的版本，而不是明确说「我做不到」。所以验收标准必须由人预先定义，而不是事后从产物反推。

笔者的经验法则是：**L3 适合「边界清晰、验收可自动化」的任务**，例如补测试、批量迁移 API、修复类型错误、给模块补齐日志。不适合「需要判断产品取舍」的任务。

## L4：意图编程的边界在哪里

L4 是标题里那个「意图编程」。它的想象图景是：你描述目标，系统自己规划、实现、验证、迭代，你只负责定义什么叫做「好」。

必须诚实地讲，**L4 目前只有非常窄的适用范围**。它在以下条件同时成立时才可能工作：

1. 目标是**可机器验证的**（有测试、有明确的输入输出、有形式化约束）；
2. 反馈循环足够快（几秒到几分钟，而不是几小时）；
3. 搜索空间有界（技术栈固定、依赖可控、接口有限）。

一旦缺少其中任意一条，L4 就会退化成一个成本更高、可控性更差的 L3。这也是为什么「一句话生成一个完整产品」在今天仍然是演示大于生产：演示的生命周期是十分钟，生产系统的生命周期是三年，而后者需要的是可维护性，不是生成速度。

对绝大多数团队，务实的做法是**把 L4 当方向，把 L2/L3 当抓手**：先让验证自动化，再让模型自主。顺序反了会很痛苦——先放权再补护栏，等于在没有安全带的时候上高速。

## 决策建议：怎么选你的层级

把上面的分析收敛成一张决策路径，可以直接用于团队讨论：

- **产物是临时的、失败了无后果**？跳到 L3 甚至 L4，不要犹豫，这是这些层级最有价值的场景。
- **产物要长期维护**？起点是 L0/L1，先把补全和对话式改写用熟，成本几乎为零。
- **仓库有测试但覆盖率不高**？优先投入 L2，先补护栏再提自动化程度，这是投入产出比最高的动作。
- **任务可并行、边界清晰**？上 L3，但要为每个任务写清验收标准。
- **目标无法机器验证**？停在 L2/L3，不要指望 L4，人工判断这一环无法被跳过。
- **团队禁止读代码的人工智能产物合入主干**？那就把这条规则写进规范，而不是靠个人自觉。

一句话版本：**顺着「验证先于自主」的顺序往上爬，而不是顺着「模型能力强弱」往上换工具。**

## 结论：分层是为了分权，不是为了排名

把 Vibe Coding 拆成 L0 到 L4，最大的作用不是排序，而是**让「谁能改、谁验证」这件事变成显式选择**。

L0 和 L1 几乎不需要治理，因为控制权还在人手里。真正需要提前设计的是 L2 及以上的护栏形态：跑哪些检查、失败几次放弃、谁最终签字、变更集多大算可评审。这些问题没有标准答案，但每个团队都应该有答案。

最后提醒一句：层级不是身份。同一个人在同一个下午，写业务逻辑时用 L1，写一次性脚本时用 L4，这是非常健康的用法。危险的是用同一套心智模型对待所有代码——那才是把工具用坏的方式。
