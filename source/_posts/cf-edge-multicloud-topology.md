# 多云边缘拓扑：让 Cloudflare 与非 Cloudflare 后端共存

真实世界的迁移几乎不是"从零开始"，而是"在已有的多云与自建环境上加一层"。这种场景下的设计目标不是追求架构纯洁性，而是**让边缘平台成为一个统一入口，同时不破坏既有系统**。本文讨论这类拓扑的几种常见形态与决策点。

## 起点：先给现有系统分类

在画拓扑之前，先把后端分成三类，因为它们对边缘的配合方式完全不同：

- **A 类：可安全暴露给边缘的 HTTP 服务**（API、渲染层），能被边缘直接回源；
- **B 类：不应暴露的敏感系统**（数据库、管理后台、消息中间件），必须走私网通道或只在内网可达；
- **C 类：非 HTTP 协议或有状态长连接**（WebSocket、gRPC、消息队列），需要专门的代理或隧道方案。

划分标准不是技术栈，而是**"是否可以被一段来自边缘的请求安全触达"**。这个判断决定了回源方式，也就决定了整个拓扑的形状。

## 形态一：边缘做统一入口，后端保持原样

最常见的形态，也最容易落地。用户流量统一进入边缘，边缘完成鉴权、限流、路由、缓存，然后回源到原有后端（通过公网 + 隧道，或专线类私网互联）。

优点：改动最小，后端不需要改代码；缺点：回源仍然是链条的一部分，性能天花板受限于回源路径。

关键设计点：

1. **入口统一**：把 DNS 全部指向边缘，源站不再对外解析；
2. **回源收敛**：边缘到后端保持少量稳定连接，避免每个 PoP 都开连接；
3. **规则前置**：能放到边缘的过滤（鉴权、限流、Bot 管理）尽量前置，降低后端压力。

```js
// 边缘做统一入口：鉴权 + 转发，后端服务保持零改动
export default {
  async fetch(request, env) {
    const url = new URL(request.url);

    // 只代理受保护的 API 前缀，其余交由平台规则处理
    if (!url.pathname.startsWith("/api/")) {
      return new Response("not found", { status: 404 });
    }

    const userId = await verifyToken(request); // 边缘统一鉴权
    if (!userId) return new Response("unauthorized", { status: 401 });

    const upstream = new URL(url.pathname + url.search, env.ORIGIN_BASE);
    const headers = new Headers(request.headers);
    headers.set("x-authenticated-user", userId); // 后端只信任来自边缘的头
    headers.delete("cookie");                    // 不再向后端传递原始 Cookie

    const resp = await fetch(upstream, {
      method: request.method,
      headers,
      body: ["GET", "HEAD"].includes(request.method) ? undefined : request.body
    });

    // 明确不缓存受保护内容
    const out = new Response(resp.body, resp);
    out.headers.set("cache-control", "no-store");
    return out;
  }
};
```

## 形态二：边缘承载一部分逻辑，后端承载重计算

当部分逻辑适合迁到边缘（鉴权、个性化拼装、A/B 分流、地理路由），而重计算与事务仍留在后端时，形成"边缘 + 后端"的分工。

分工的判断依据可以简化成一张表：

| 判断维度 | 优先放边缘 | 优先留后端 |
|---|---|---|
| 延迟敏感度 | 高（用户可感知） | 中低 |
| 有无状态 | 无状态或弱状态 | 强事务、需锁 |
| 依赖类型 | 标准 Web API | 原生扩展、本地文件 |
| 执行时长 | 短（毫秒级） | 长（秒级及以上） |
| 变更频率 | 高（需快速灰度） | 低 |
| 数据位置要求 | 允许在边缘处理 | 需固定区域 |

注意最后两行：**变更频率高、适合快速灰度的逻辑放边缘收益最大**；而**有数据位置要求或强事务需求的逻辑必须留在后端**。

## 形态三：多后端按区域分流

当后端本身分布在多个云与多个区域时，边缘可以根据用户属性或请求特征选择回源后端。常见策略：

- **按地理**：用户在不同区域，回源到就近后端；
- **按租户**：企业客户绑定到专属后端环境；
- **按灰度**：新版本只服务小比例流量；
- **按健康状态**：某后端异常时自动切走。

```js
// 多后端分流：按租户 + 健康状态选择上游
const ORIGINS = {
  default: "https://origin-a.example.com",
  enterprise: "https://origin-b.example.com"
};

export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    const tenant = request.headers.get("x-tenant") || "default";
    const base = ORIGINS[tenant] || ORIGINS.default;

    try {
      const upstream = new URL(url.pathname + url.search, base);
      const resp = await fetch(upstream, { signal: AbortSignal.timeout(5000) });
      if (resp.status >= 500) throw new Error("upstream 5xx");
      return resp;
    } catch {
      // 明确降级：返回可理解的错误，而不是长时间挂起
      return new Response(JSON.stringify({ error: "upstream_unavailable" }), {
        status: 503,
        headers: { "content-type": "application/json", "retry-after": "5" }
      });
    }
  }
};
```

`AbortSignal.timeout` 那一行是这类拓扑的关键细节：**没有超时的跨云回源会导致请求堆积，把局部故障放大成全站故障**。

## 决策对照：三种形态的取舍

| 维度 | 形态一（统一入口） | 形态二（分工） | 形态三（多后端分流） |
|---|---|---|---|
| 后端改动量 | 无 | 中（拆分逻辑） | 中（需健康探测） |
| 性能收益 | 中 | 高 | 中高 |
| 运维复杂度 | 低 | 中 | 高 |
| 灰度能力 | 强（入口层） | 强 | 强 |
| 故障影响面 | 入口是单点关注区 | 需处理两侧不一致 | 需处理路由误判 |
| 适合团队规模 | 小到中 | 中到较大 | 较大（有多环境需求） |

> 经验法则：**先做形态一，验证边缘的稳定性与可观测性，再决定是否推进到形态二**。跳过验证直接做逻辑迁移，一旦边缘侧出现难以定位的问题，回退成本会很高。

## 两个高发问题与处理

**问题一：DNS 切换的"半生效"状态**
把解析从源站切到边缘时，由于各级递归解析器缓存，会出现一段时间内新旧入口并存的局面。处理方式：切换前先降低 TTL 并等待生效，切换后**保持源站入口可用一段时间**（返回重定向或直接服务），观察流量降到零再关闭。

**问题二：双重代理导致的头信息混乱**
链路是"用户 → 边缘 → 自有网关 → 后端"时，客户端 IP 与协议信息会被多层覆写。处理方式：**明确每一跳的信任关系**，只接受上游注入的专用头，并在最内层做一次规范化，形成单一可信来源。

## 成本与团队协作

多云场景的隐性成本往往不在带宽，而在**认知负担**：两套控制台、两套权限模型、两套日志系统、两种排障习惯。可行的缓解手段：

1. **配置即代码**：把两边的关键配置纳入版本管理，减少"记得改但漏了"；
2. **统一日志出口**：无论来源，先汇聚到一个查询入口，排障时不必来回切换；
3. **明确责任矩阵**：哪个团队负责边缘规则、哪个团队负责后端、跨界的变更由谁审批；
4. **定期链路演练**：模拟单侧不可用，验证切换动作真的有效，而不是停留在文档上。

## 结语

多云边缘拓扑的设计核心不是"用上什么新技术"，而是**在既有系统上定义清晰的信任边界与故障边界**。把入口统一、把回源收敛、把降级显式化，就能在不打乱现有系统的前提下获得边缘的主要收益；至于是否进一步把逻辑迁到边缘，应当由实测收益而不是架构偏好来驱动。
