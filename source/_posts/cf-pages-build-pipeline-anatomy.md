# Cloudflare Pages 构建管线解剖：从 Git 提交到全球边缘的完整链路

大多数团队接入 Pages 的过程只有五分钟：连仓库、填 `build command`、填 `output directory`、点部署。之后这条链路就变成了理所当然的存在，直到某天构建突然从 90 秒变成 6 分钟，或者某个环境变量在预览环境里神秘消失，才会有人回头去问：这中间到底发生了什么。

本文不复述官方文档的配置项清单，而是把 Pages 的构建管线拆成可推理的四个阶段，然后针对每个阶段讨论缓存、约束与调优空间。

## 阶段拆解：一次 push 之后的四个动作

从工程视角看，Pages 的构建管线可以抽象成下面四个串行阶段：

1. **事件接收与排队**：Git provider 通过 webhook 通知 Pages 有新的 commit，Pages 为这次提交创建一个 deployment 记录。同一分支上的新提交会让旧 deployment 快速失效（superseded）。
2. **环境准备**：拉起一个一次性的构建容器，检出仓库到该 commit，恢复依赖缓存，按项目配置注入环境变量（分为生产环境与预览环境两套）。
3. **执行构建**：运行你指定的构建命令。这一步对 Pages 而言是完全不透明的——它不知道你在跑 `hexo generate` 还是 `next build`，只知道退出码。
4. **产物上传与分发**：把输出目录上传到对象存储，生成不可变的 deployment 子域，同时按分支策略决定是否更新生产域名指向。

理解这四段划分的价值在于：当构建变慢或失败时，你能立刻定位问题归属，而不是笼统地抱怨"Pages 又抽风了"。

## 构建容器：约束比性能更值得关注

Pages 的构建环境是一个受控的容器，而不是一台你可以随意 SSH 进去的机器。这意味着你要接受几类约束：

- **运行时版本受控**。Node 版本通常由项目内的 `.nvmrc`、`engines` 字段或环境变量决定，但可选择范围有限。写死一个过旧的版本会在几个月后被移除。
- **构建超时存在上限**。构建不是可以无限跑下去的任务，长任务最终会被强制终止，这一点在做全量静态生成的大型站点上尤其容易踩坑。
- **磁盘与内存是共享的**。依赖安装、构建产物、缓存都挤在同一块临时空间里，`node_modules` 加产物体积超过阈值时会以奇怪的方式失败。
- **构建容器无持久状态**。任何你以为"上次跑留下了"的文件都不存在，除了显式声明的缓存目录。

```bash
# 一个最小但信息完整的构建配置示例（.node-version + package.json scripts）
# 1. 固定运行时
echo "20.11.1" > .node-version

# 2. 在 package.json 中声明构建脚本，避免直接把长命令写进 Pages 面板
# "scripts": {
#   "build": "node ./scripts/prebuild-check.js && hexo generate"
# }

# 3. 本地复现构建环境时，至少对齐 Node 版本与依赖安装方式
nvm use
npm ci --no-audit --no-fund
npm run build
```

把构建命令收敛到 `package.json` 里而不是面板里，是一个被低估的实践：它让本地、CI、Pages 三处跑的是同一条命令，行为差异会大幅缩小。

## 缓存策略：命中率决定构建时间

构建耗时的大头通常不在你的构建命令本身，而在依赖安装。Pages 提供依赖缓存机制，但命中与否取决于几个细节：

| 缓存维度 | 命中条件 | 失效后的代价 | 可操作建议 |
|---|---|---|---|
| 包管理器缓存 | lockfile 未变化 | 重新下载全部依赖 | 提交 lockfile，不要在构建时 `install` 一个漂移的版本 |
| 构建产物缓存 | 你的工具自己实现 | 全量重新生成 | 增量构建需要框架支持，静态生成器通常不支持 |
| 构建镜像层 | 由平台管理 | 环境冷启动变慢 | 无法直接控制，只能减少依赖数量 |

一个实践中的经验法则是：**把 lockfile 当作构建契约**。如果你在构建脚本里跑 `npm install` 而不是 `npm ci`，那么每次构建都可能解析出不同的依赖树，缓存命中率随之崩塌，同时引入不可复现的风险。

```toml
# wrangler.toml 片段：如果构建产物需要配合 Pages Functions 一起工作
name = "my-site"
pages_build_output_dir = "public"

# 构建产物的目录必须与 Pages 面板里的 output directory 保持一致
# 否则会出现「构建成功但页面 404」这种最令人困惑的故障
```

> **经验法则**：构建时间超过 3 分钟后，应先优化依赖安装，再考虑优化构建命令本身。多数项目的耗时结构是「依赖 70%、构建 30%」。

## 环境变量与预览环境的语义差异

Pages 把环境分成生产与预览两类，但真正的复杂性在于：预览环境不是生产的缩小版，它们的语义完全不同。

- **预览环境的域名是每次部署唯一的**，因此任何把域名写死进构建产物的做法都会在预览里出问题。
- **环境变量按环境隔离**，但某些框架会在构建期把变量内联进产物，导致预览环境拿到生产值。
- **预览部署默认不更新生产域名**，这对回滚很友好——你可以先把某个历史 deployment 提升为生产，而不必重新构建。

这就引出一个常被忽略的结论：**构建期变量与运行期变量必须分开管理**。构建期变量进入产物后就不可更改，适合放公开的配置；运行期变量应由 Pages Functions / Workers 在请求时读取，适合放敏感值。

## 分支策略：把流水线画成决策树

一个成熟团队通常不会让所有分支都触发同一条链路。下面是一个可参考的分支到部署的映射策略：

- `main` / `master`：触发生产部署，产物直接对应用户可见。
- `preview/*` 或 PR 分支：触发预览部署，生成独立子域，用于评审。
- `docs/*`：如果只改文档，可以配置为跳过构建或用更轻的命令。
- `release/*`：用于发布候选，通常会额外挂一层灰度域名。

Pages 允许为不同分支配置不同的构建命令与环境变量，这一点在做「文档站与主站共用仓库」时特别有用——你不需要两个仓库，只需要两条构建路径。

## 缩短构建时间的可操作清单

把前面几节落到操作层面，可以总结成一张清单：

1. 用 `npm ci` / `pnpm install --frozen-lockfile` 替代 `install`，保证可复现并提升缓存命中。
2. 把长命令收进 `package.json` 的 script，面板里只留一个短入口。
3. 用 `.node-version` 或 `engines` 显式固定运行时版本。
4. 清理不必要的构建依赖，把只在本地用到的工具移到 `devDependencies` 之外或独立脚本。
5. 对大型站点做产物分片或延迟生成，避免单次构建触及超时上限。
6. 在 CI 中加一步「产物大小检查」，防止无意中把几百 MB 的资源带进部署。

最后一点尤其重要：Pages 的部署产物会分发到全球边缘节点，产物体积不仅影响构建上传时间，也影响用户的首字节时间。构建优化与运行时优化在这里是同一件事。

> **说明：** 本文基于 Cloudflare Pages 公开的构建与部署机制进行工程化解读，具体配额、超时上限与运行时版本以 Cloudflare 官方最新文档为准；文中涉及的耗时比例为经验观察，不作为权威统计数据。观点部分为笔者基于实际项目经验的判断，欢迎按自身场景验证。
