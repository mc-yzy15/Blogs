# 边缘 SQLite 的 Schema 迁移：把 DDL 当作可回滚的发布流程

应用代码可以灰度、可以回滚、可以同时跑两个版本，但数据库 schema 只有一个。在边缘 SQLite 场景下，这个矛盾会被放大：因为边缘应用是就近执行的，多个版本的 Worker 可能同时在线，它们会同时按自己的假设读写同一套表结构。本文讨论的是如何在这种约束下做 schema 迁移，而不是教 ALTER TABLE 的语法。

## SQLite 的 DDL 特性如何约束迁移设计

SQLite 有一个与其他数据库很不相同的特性：它的 `ALTER TABLE` 能力非常有限。长期以来它只能做「加列」「重命名表」「重命名列」这类操作，而**改列类型、改约束、删列、调整主键**这些需求，需要通过「建新表 → 复制数据 → 删旧表 → 重命名」这一整套重建流程来完成。这个流程本身是标准做法，但它有一个直接的工程后果：**很多看似微小的 schema 变更，其实是一次数据搬运**。

数据搬运在我们关心的环境里有三个代价。第一是行读写开销，复制整表意味着读一遍写一遍，这与按行计费的模型直接相关。第二是执行时长，大表的复制可能超出单次请求或单条语句的时长限制。第三是原子性边界，重建过程中应用若还在写旧表，数据就会分叉。

另一个特性是 SQLite 对表结构变更的元数据操作会短暂锁表。在单机 SQLite 上这通常不是问题，但在托管的多读副本架构下，DDL 需要先在主库执行，再传播到副本，期间不同副本可能处于不同的 schema 版本。这就要求迁移设计必须假设「新旧 schema 会共存一段时间」。

这两条特性合起来，给出了迁移设计的第一原则：**任何迁移都必须是向前兼容的，即旧代码在新 schema 上仍能正确运行。**

## expand-contract：把一次变更拆成三个阶段

为了让新旧代码与新老 schema 能安全共存，实践中最可靠的模型是 expand-contract，也叫「扩展-收缩」。它把一次 breaking change 拆成三个可独立发布的阶段。

- **扩展（expand）**：只做加法。新增可空列、新增表、新增索引。这一步不修改任何既有结构，因此新旧代码都能正常运行。旧代码忽略新列，新代码在新列写入默认值。
- **双写与回填（migrate）**：新代码同时写新旧两处表达（新旧列、新旧表），并启动一个幂等的回填任务把历史数据补齐。此时读仍然走旧路径，保证结果稳定。
- **收缩（contract）**：等确认所有读路径都已切到新结构、且回填完成之后，再删除旧列或旧表。这一步是不可逆的，要放在所有灰度完成之后单独执行。

这个模型的关键在于**把不可逆操作推到流程最后**，让前面每一阶段都可以安全回滚。回滚的定义也随之变得清晰：扩展阶段回滚只需取消发布，收缩阶段才需要真正的数据恢复预案。

举一个具体的例子：把 `users.name` 拆成 `first_name` 与 `last_name`。

```sql
-- 阶段 1：expand —— 只加列，可空，不动旧列
ALTER TABLE users ADD COLUMN first_name TEXT;
ALTER TABLE users ADD COLUMN last_name TEXT;

-- 阶段 3：contract —— 确认无读依赖后，重建表去掉旧列
CREATE TABLE users_new (
  id INTEGER PRIMARY KEY,
  first_name TEXT NOT NULL DEFAULT '',
  last_name TEXT NOT NULL DEFAULT '',
  email TEXT UNIQUE
);
INSERT INTO users_new (id, first_name, last_name, email)
  SELECT id,
         COALESCE(first_name, name, ''),
         COALESCE(last_name, ''),
         email
  FROM users;
DROP TABLE users;
ALTER TABLE users_new RENAME TO users;
```

注意阶段 3 里的 `COALESCE`：它会优先取已经回填好的新列，回退到旧列。这类兜底表达式是让重建过程在「回填尚未 100% 完成」时依然安全的常用手法。

## 迁移与代码发布的顺序约束

有了三阶段模型，还需要明确它与代码发布的相对顺序。核心规则只有一条：**先发布能兼容新旧两种 schema 的代码，再改 schema**。

具体到两个方向：

- **加列**：先发布会写新列、但读旧列的代码，再执行 DDL。因为加列本身向下兼容，这个顺序的风险主要来自「代码先写了新列但列还不存在」，所以更稳妥的顺讯是先 DDL 再发代码——前提是 DDL 纯粹是加法且不阻塞。
- **删列**：必须先让所有读路径停止依赖该列，再删除。这要求你能确信没有旧版本 Worker 仍在读取它。

在边缘环境里，「是否还有旧版本在跑」这个问题并不容易回答。Worker 的旧部署可能在短时间内仍然接收流量，长连接（如 WebSocket）会延长旧版本的生命周期。因此**删列前的观察期应当以小时计，而不是以分钟计**。这是边缘场景相对于传统单体应用的一个重要差异。

下表对比了不同变更类型在三个阶段中的风险分布，可以作为评审时的速查表。

| 变更类型 | expand 阶段风险 | migrate 阶段风险 | contract 阶段风险 | 备注 |
|---|---|---|---|---|
| 加可空列 | 极低 | 无 | 无 | 最常见也最安全 |
| 加非空列 | 低（需默认值） | 无 | 无 | 默认值需与业务语义一致 |
| 改列类型 | 低 | 中（回填正确性） | 高（数据不可逆） | 必须走重建表流程 |
| 拆列/合列 | 低 | 中到高 | 高 | 需双写与回填 |
| 加索引 | 低 | 无 | 无 | 注意写放大与存储 |
| 删列 | 无 | 无 | 高 | 必须确认无读依赖 |
| 改主键 | 极低 | 中 | 高 | 通常等价于重建全表 |

## 回填任务的幂等与断点续跑

数据回填是整个流程里最容易出事故的环节，因为它要处理的数据量大、执行时间长、还可能中途失败。把它写成一次性脚本是危险的，正确的做法是把它当作一个可重复执行的作业。

设计要点有四个：

1. **幂等的更新条件**。回填语句应当只更新「尚未迁移」的行，例如 `WHERE first_name IS NULL`，这样重复执行不会产生副作用，也不会因为并发而互相覆盖。
2. **按主键区间分批**。用 `WHERE id > ? ORDER BY id LIMIT ?` 推进游标，避免 `OFFSET` 在大表上越来越慢。
3. **每批独立提交**。批次大小与事务体量限制匹配，单批失败不影响已完成部分。
4. **可观测的进度**。记录已处理的最大主键，既作为断点，也作为进度指标。

```sql
-- 幂等回填：只处理尚未迁移的行，按主键推进
UPDATE users
SET first_name = COALESCE(first_name, substr(name, 1, instr(name || ' ', ' ') - 1)),
    last_name  = COALESCE(last_name, '')
WHERE id > ?
  AND id <= ?
  AND first_name IS NULL;
```

这个模式还有一个额外好处：它天然支持在流量低峰期慢速推进，把回填对线上读写的影响摊平。如果你的环境有调度能力，把回填做成定时任务比一次性执行更稳。

## 迁移的可观测性与回滚预案

一个没有被观测的迁移等于一次盲飞。最低限度需要采集的信息包括：当前 schema 版本、已回填行数占总数的比例、迁移期间的错误率与延迟变化、以及新旧读路径的结果差异比例。

关于最后一项，有一个非常实用的技巧：在双写阶段**同时读新旧两处并比对结果**，把不一致的样本记录下来但不影响返回。这能让你在真正切换读路径之前就发现回填逻辑的缺陷，而不是等用户报错。

回滚预案则要按阶段区分：

- expand 阶段：直接回滚代码即可，schema 的加法无需撤销。
- migrate 阶段：回滚代码会停止双写，但已回填的数据保留，通常无害；需要确认回滚后的读路径能正确解释这些数据。
- contract 阶段：这是唯一真正不可逆的阶段。执行前应当有一次可验证的数据快照，并演练过从快照恢复的流程。

> 一条必须写进规范的规则：**收缩阶段永远单独发布，不与任何功能变更混在同一次上线里**。把不可逆操作和功能变更耦合在一起，是排查事故时最让人头疼的组合。

## 团队实践：把迁移纳入版本控制与流程

最后是流程层面的约定。成熟的团队会把迁移脚本纳入版本控制，用编号或时间戳排序，并由 CI 在部署前自动执行未应用的迁移。这样做的好处是迁移历史可审计、环境可重建、评审时能看清变更范围。

配套的约定还包括：

- 每条迁移脚本必须写明**对应的回滚方案**，哪怕回滚只是「从快照恢复」。
- 迁移脚本不允许包含业务逻辑，只做结构变更与数据搬运。
- 迁移前必须评估行触达量，超过一定规模的要走分批与低峰执行。
- 所有迁移在预发布环境至少完整跑过一次，包括回滚演练。
- 破坏性变更必须在 PR 描述里显式标注，并说明验证方式。

把这五条固化下来之后，数据库变更就从「上线前夜的手工操作」变成了普通的一次发布。这是边缘数据库项目从原型走向长期维护的必要一步。

> **说明：** 本文为原创技术分析，讨论 SQLite 与 D1 场景下的 schema 迁移方法论。SQLite 对 DDL 的支持能力与 D1 的执行与配额限制均可能随版本更新而变化，请以官方最新文档为准。文中 SQL 为讲解用途，涉及重建大表时请在实际环境中先验证耗时与锁影响。
