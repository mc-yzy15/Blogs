# 浏览器 Agent 的技术栈拆解

当 GPT-6 把"操作电脑"变成模型能力，浏览器 Agent（能自主打开网页、填表、点击、完成任务的 AI）成为最热门的落地形态。但做过的人都知道：**让模型"看懂"网页容易，让 Agent"稳定操作"很难。** 拆开一个生产级浏览器 Agent，技术栈大致分三层。

## 第一层：网页理解（页面怎么"看"）

模型读网页有三种路径，各有取舍：

1. **DOM/无障碍树（Accessibility Tree）**：直接把页面的结构化语义（按钮、输入框、链接）喂给模型——精确、省 token，是当前主流首选；
2. **纯视觉（截图）**：模型直接看渲染后的截图——最接近人眼，能处理 Canvas、复杂图表，但 token 消耗高、对像素级操作不稳定；
3. **混合方案**：以无障碍树为主干，遇到动态内容或视觉元素时切截图补充——工程上的折中主流。

## 第二层：操作执行（手怎么动）

理解了页面，Agent 还要"动手"。可靠性设计是关键：

1. **选择器 vs 坐标**：优先用语义选择器（按钮 ID/角色）定位元素，坐标点击只作兜底——页面布局一变，坐标就废了；
2. **状态验证**：每次操作后要验证页面状态（是否真的跳转/提交成功），而不是"点完就算"；
3. **失败重试与恢复**：弹窗、验证码、加载慢——Agent 要能识别异常、回退重试，而不是卡死。

## 第三层：任务闭环（脑子怎么想）

最上层的任务层负责"规划与验证"：

1. **目标分解**：把"帮我订机票"分解成"搜索→筛选→填表→支付→确认"的可执行步骤；
2. **中间校验**：关键节点（如支付前）停下确认或检查金额，避免一步错步步错；
3. **结果断言**：任务完成的标准要可验证（"预订成功"的凭证是什么），而不是"页面看起来差不多了"。

## 三个工程陷阱

1. **验证码与反爬**：真实网站有各种人机验证，浏览器 Agent 的规模化运营绕不开合规问题——先想清楚你的使用边界；
2. **会话与登录态**：管理 Cookie、多账户隔离、避免污染用户真实会话——这是最容易翻车的工程细节；
3. **成本模型**：长任务的 token 消耗可能很惊人，截图方案尤其费钱——按"每次操作成本"做预算。

## 结语

浏览器 Agent 的成熟度，正从"能做 Demo"走向"能干活"。但它的工程门槛比看起来高得多——**模型负责聪明，工程负责可靠。** 如果你要在这条赛道上做产品，请把 80% 的精力花在"操作可靠性"上，而不是继续追更强的模型。
