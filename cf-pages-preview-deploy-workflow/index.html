预览部署工作流设计：用 Cloudflare Pages 把评审成本压到最低

「每个 PR 自动生成一个预览链接」这件事，演示起来只要十分钟，但在真实团队里跑上三个月，就会积累出一堆脏问题：预览链接被外部爬虫收录、预览环境往生产数据库写数据、评审者看到的是三天前的缓存版本、回滚时不知道该回滚到哪个 deployment。

这些问题的共同点是：它们都不是 Pages 的功能问题，而是工作流设计问题。本文讨论如何在 Pages 提供的能力之上，设计一套能长期运行的预览部署工作流。

预览部署真正的价值在哪里

先澄清一个常见误解。预览部署的价值不在于”给非技术人员看效果”——那个需求用截图或本地服务器也能满足。它真正解决的是下面三类问题：

  • 环境相关缺陷只能在真实环境暴露。路由重写、资源路径、跨域头、缓存策略这些问题在本地往往表现正常。
  • 评审需要上下文而非代码。产品与设计评审的是”行为”，不是 diff。
  • 变更影响面需要可验证。特别是改动构建配置、CDN 缓存规则、重定向表时，只有真实部署能验证。

因此预览部署的设计目标应该是：让一次部署尽可能接近生产，同时把它的副作用降到零。这个目标里，”副作用”才是难点。

分支命名约定：让 URL 成为可读的元数据

多数团队会把预览链接直接丢在聊天窗口里，然后几周后没人知道哪个链接对应哪个功能。解决方式是把信息编码进分支名，因为 Pages 会用分支名生成预览子域。

一个可用的约定是分层命名：

  1. feat/<issue-id>-<slug>：功能分支，如 feat/412-checkout-retry。
  2. fix/<issue-id>-<slug>：缺陷修复分支。
  3. exp/<slug>：纯实验分支，允许不稳定，允许随时删除。
  4. release/<version>：发布候选，通常需要额外一层保护。

这样生成的预览域名天然携带语义，回看历史时有据可查。反过来，如果分支名全是 update、test2、tmp，预览部署的信息价值会被迅速稀释。

数据隔离：预览环境最容易出事的地方

预览部署最危险的场景是：它看起来像个玩具，但它连的是真数据库。用户点一下”删除”，生产数据就没了。

对于前后端一体的站点（例如 Pages 静态前端 + Pages Functions 后端），几种隔离策略按成本从低到高排列：

策略 实现方式 隔离强度 适用场景
只读预览 预览环境注入只读凭据 中 纯展示型评审
独立数据集 预览使用独立 D1 / KV 实例 高 需要写入验证的功能
影子数据库 定期从生产脱敏同步 高 需要真实数据结构
完全模拟 使用内存或 mock 层 最高 单元级验证、无后端依赖

对多数团队而言，独立数据集是性价比最高的选择：Pages 的环境变量机制允许预览与生产绑定不同的绑定（binding），你只需要在配置层面做一次分流，就能让预览环境永远碰不到生产数据。

风险提示：不要把 D1、KV 或 R2 的生产凭据放在预览环境变量里。一旦预览部署的链接泄露（这几乎必然发生），凭据就等于公开。

访问控制：预览链接的默认安全姿态

这里需要区分两件事：平台层面的访问控制与应用层面的访问控制。

平台层面可以限制整个预览域名的访问（例如通过 Access 之类的身份层），应用层面则是在自己的代码里判断当前是否预览环境。两者的正确用法是：

  • 内部项目：优先用平台层控制，因为它是”默认拒绝”的姿态，漏配的代价是访问被挡，而不是数据泄露。
  • 开源或公开评审项目：预览链接本身可能就需要公开展示，此时应用层要显式处理”这是预览”的语义，例如加一个顶部横幅、禁用支付入口、禁止提交表单。

一个常见的失误是：只在预览环境加”禁止支付”的代码分支，而忘记预览环境同样会调用真实的第三方 API。正确做法是把所有外部副作用统一收口到一个配置开关，预览环境默认全部关闭。

缓存与 SEO：两个容易被忽略的副作用

缓存污染。如果预览域名与生产域名共享 CDN 缓存键，或者预览环境的响应被写入了共享的 KV 缓存，你会看到”预览内容串到生产”的诡异现象。避免方式很简单：让缓存键包含部署标识，或者让预览环境完全不写共享缓存。

搜索引擎收录。预览域名的内容通常与生产重复，如果被收录会造成内容重复问题，更糟的是可能让未完成的页面出现在搜索结果里。推荐的双保险是：

同时配合响应头 X-Robots-Tag: noindex，因为某些爬虫更信任响应头而非 meta 标签。还需要注意的是：如果预览环境存在未公开的功能描述，noindex 并不能阻止内容被读取，只是阻止被索引。

  • 使用 noindex 而非 robots.txt：后者对未收录的域名约束力有限，且是全局的。
  • 在预览环境关闭 sitemap 输出。
  • 在预览环境关闭社会化分享的预览图抓取，避免生成指向预览域名的卡片。
  • 定期清理陈旧的预览部署，减少被发现的表面积。

回滚与清理：工作流的最后一段

预览部署的工作流必须包含”结束”这一步，否则三个月后你会面对几百个僵尸部署。

回滚方面，Pages 的 deployment 是不可变的，这使得回滚变得异常简单：直接把一个历史 deployment 重新提升为生产即可，无需重新构建。这比”重新跑一次旧 commit 的构建”可靠得多，因为旧 commit 的依赖可能已经无法解析。

清理方面，建议在上线后自动删除对应的预览部署，或者按保留策略定期清理。判断标准可以很简单：已合并或已关闭的分支，其预览部署应在一个固定周期后消失。

经验法则：预览部署应当”用完即弃”，把它当成一次性的评审设施，而不是长期托管的第二个站点。丢弃的默认值应该是”删除”，而不是”保留”。

把以上几节合起来看，一套健康的预览工作流大约长这样：分支名承载语义、预览与生产绑定分离、外部副作用默认关闭、索引被双重阻断、部署生命周期随 PR 结束而终结。做到这几点，预览部署才会从”看起来很酷的演示”变成真正降低评审成本的基础设施。

说明： 本文讨论的是预览部署的工作流设计方法论，不涉及任何特定平台的定价或配额承诺；文中配置片段为示意写法，实际字段与能力请以 Cloudflare 官方最新文档为准。文中的经验法则来自工程实践总结，不同团队规模下可能有不同取舍。
