Agent 账单失控：token 成本治理三板斧

聊天机器人的 token 账单是可预测的，Agent 的不是——一个”看起来简单”的任务可能包含几十次模型调用、几万 token 的上下文往返。许多团队在 Agent 上线第一周就被账单教育了：Agent 的成本问题，必须在架构阶段就治理，而不是等账单来了再救火。

为什么 Agent 这么烧钱

Agent 的成本结构与传统对话完全不同：

  1. 调用次数爆炸：一次任务 = 规划 + N 次工具调用 + N 次结果反思，每次都是一次完整的模型往返；
  2. 上下文膨胀：工具返回结果、历史步骤、项目背景都在往上下文里塞，输入 token 是最大的成本黑洞；
  3. 失败重试成本：Agent 出错重试不是免费重来——每次重试都重新烧一遍钱。

三板斧之一：压缩（输入瘦身）

  1. 工具结果裁剪：工具返回 5000 token 的数据，只把相关的 500 token 喂给模型——别让”全量返回”白白烧钱；
  2. 历史摘要化：长任务不需要完整保留每轮对话，跑几步就压缩一次历史，只留决策要点；
  3. 上下文预算：给每类任务设上下文上限，超过就强制精简或切换更便宜的模型档。

三板斧之二：路由（模型分级）

不是所有调用都需要旗舰模型：

  1. 按任务复杂度分级：简单判断用 Flash 档，复杂推理才升级旗舰——成本差异可能是一个数量级；
  2. 分类器前置：用一个便宜模型先判断”这个任务值不值得用贵的”，避免大炮打蚊子；
  3. 小模型优先：很多 Agent 内部步骤（格式化、简单判断）用小模型完全够用，旗舰留给真正的难点。

三板斧之三：缓存（避免重复烧钱）

  1. 结果缓存：相同输入的工具调用结果（尤其是搜索、API 查询）直接命中缓存，不重复调用模型；
  2. Prompt 缓存：系统提示、项目背景这类稳定上下文用厂商的 prompt 缓存能力，价格能降一个量级；
  3. 任务级复用：相似的子任务结果（常见问题的标准处理）沉淀复用，而不是每次重新推理。

治理的制度保障

光有技术手段不够，还需要配套机制：

  1. 预算告警：按用户/任务/团队设置 token 预算与告警线，超限自动降级；
  2. 成本可观测：每个任务结束时记录 token 消耗与成本，形成”任务成本报表”——不可观测的成本无法治理；
  3. 定期成本复盘：每周看一次”最烧钱的 10 类任务”，针对性地优化——成本治理是持续工程，不是一次性配置。

结语

Agent 的成本失控，大多不是模型太贵，而是工程太糙：上下文塞太多、路由不分级、缓存没做。三板斧执行到位，通常能把成本压下一个数量级。在 Agent 的商业化里，”能用”和”能赚钱”之间，隔着的就是这份成本工程。

**说明：**本文为 Agent 成本治理实践总结，具体方案请结合模型与业务场景落地。
