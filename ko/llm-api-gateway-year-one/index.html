自建 LLM API 网关一年复盘：鉴权、限流、渠道与账单，我踩过的坑

自建 LLM API 网关一年复盘：鉴权、限流、渠道与账单，我踩过的坑

去年我把自己搭的 AI API 网关正式对外开放（就是博客里的「瀛光 API」），到现在刚好一年出头。这一年里，被 DDoS 问候过、被上游渠道限流过、被账单教过做人、也被自己写出来的安全漏洞吓出一身冷汗。这篇不是架构圣经，是一个小团队/个人开发者视角的实战复盘，把那些「书上不会写、踩了才知道」的坑尽量讲清楚。

为什么要自己搭网关，而不是直接卖上游的 key

先说动机。早期我做 AI 相关的小工具，直接在代码里调各家官方 API，各自维护 key、各自算账。很快发现三个痛点：

  1. 多供应商切换太痛。 官方 API 的格式、鉴权、限流策略各不相同，每次换渠道都要改代码。
  2. 账单和用量完全黑盒。 用户用了多少、花了我多少钱、谁在薅羊毛，统统不清楚。
  3. key 泄露的代价太高。 官方 key 一旦泄露，要么被刷爆，要么只能整把作废重来。

所以我才决定在中间加一层「网关」：对外统一接口格式（OpenAI 兼容），对内做渠道路由、鉴权、配额和计量。 用户在网关拿一把独立的 key，我可以在中间做限流、做熔断、做账单，出了事也只需吊销一把子 key，不伤上游。

第一个大坑：鉴权方案，我推翻过三次

第一次：一把主 key 走天下

最早期图省事，所有用户共享网关自己的主 key，靠 IP 或者简单 token 区分。结果不言而喻：一个用户泄露或分享 key，所有人都跟着遭殃，而且根本查不出是谁。

第二次：每用户一把 key，但存在数据库明文里

后来改成每用户一把 key，但这把 key 直接明文存库。直到某天我发现，只要有数据库读取权限（哪怕是一次备份泄露），所有用户的 key 就全完了——这等于把保险柜钥匙和保险柜放在一起。

第三次：存哈希，验证用安全比较

现在的做法是：网关为用户生成 key 时，只在库里存 key 的哈希值，验证时用恒定时间比较（防时序攻击）。用户拿到的原始 key 只在创建时展示一次，之后谁也无法从数据库里还原出来。

这条我建议所有做 key 管理的人直接抄走：密钥类字段永远不存明文，永远不打印进日志，创建后只显示一次。

第二个大坑：限流，粒度比额度更重要

一开始我以为限流就是「每个用户每天 X 次调用」。直到被真实流量教育，才明白限流至少有三个维度要分开做：

  1. 按用户限：防单个用户刷爆渠道。
  2. 按并发限：一个用户开 50 个并发请求，能把上游渠道打挂，也会拖垮整个网关。
  3. 按渠道限：同一个上游渠道的全局配额必须由网关统一守，否则「用户没超，渠道被总量打爆」的情况会反复出现。

另外还有一个反直觉的经验：限流要分「硬限」和「软限」。 硬限是铁律，超了就 429；软限是业务层的缓冲，比如提示用户即将触顶、自动降级到备用渠道。全上硬限，用户体验会很难看；全不上，账又会很难看。

第三个大坑：渠道管理，熔断和自动切换缺一不可

多渠道接入后，真正的难点不是「接进来」，而是「跑挂了怎么办」。

我经历过最典型的事故是：某上游渠道某天下午开始大面积超时，但我的网关还在傻乎乎地把流量全打过去——结果用户侧表现为「全线超时」，而我这边日志里全是上游的慢响应。那天我明白了一件事：网关的核心价值不是转发，是「感知上游健康状态并自动决策」。

现在的做法是：

  • 每个渠道配超时时间和连续失败阈值；
  • 触发阈值后自动把该渠道熔断，流量切到备用渠道；
  • 熔断渠道进入半开探测状态，恢复健康后再逐步放量回来；
  • 所有切换都要有日志和告警，不能悄悄发生。

这套机制上线后，上游出问题对用户的影响从「全体不可用」降到了「极少感知」。

第四个大坑：账单对账，我通宵过不止一次

如果说鉴权和限流是技术债，那账单就是纯纯的财务债，而且它最磨人。

不同渠道的计费口径五花八门：有的按输入输出分开计、有的按缓存命中与否计、有的按「tokens 总量 + 固定费用」混合计。更麻烦的是，各家对 token 的统计口径本身就不一致，同一个请求在两个渠道的「tokens 数」可能差出 10%。

踩出来的教训是三条：

  1. 网关必须自己计量，不能信任上游账单。 每个请求的输入/输出 tokens、缓存情况、模型、渠道，全都要在网关侧留痕。对账时以网关计量为主、上游账单为辅，差得多就说明有 bug 或口径问题。
  2. 用户账单要按「网关的计量」结算，而不是按上游账单，否则上游一调口径你的账就乱了。
  3. 缓存计费要单独盯。 上下文缓存是省钱利器，但它让「成本预估」变得很不确定，别在缓存命中率上想当然。

第五个大坑：安全，一次渗透测试把我吓醒

这一年里最让我后怕的，不是流量事故，而是一次针对网关的安全审查。一查之下才发现，自己写过的地方有好几个「我以为没问题」的洞：

  • SSRF：网关要转发到各种上游地址，如果上游 URL 可以被用户输入控制，就存在让服务器去访问内网/云元数据接口的风险。后来我给所有出站请求加了「协议白名单 + 目标 IP 校验 + 禁止自动跟随重定向」，把内网和云元数据地址彻底挡在门外。
  • 路径与文件处理：凡是涉及文件名、路径拼接的地方，一律用路径库规范化并做边界校验，拒绝任何包含 ..、盘符之类的输入。
  • 密钥与日志：排查日志时发现早期代码会把完整的 key 打进去——这可能是我最严重的失误。现在所有日志组件都会先做脱敏。
  • 管理接口：曾经有不需要鉴权的调试接口挂在公网，虽然是「内部工具」，但等于给攻击者留了后门。所有管理端点现在都要求独立的管理鉴权，不跟用户体系混用。

那次审查之后我给自己的规矩是：凡是暴露在公网、处理外部输入的代码，先按「会被攻击」来写，再按「会被正常使用」来优化。 顺序反了，迟早出事。

可复用的检查清单

如果你也在做类似的东西，下面这份清单可以直接拿去自检：

  • 密钥/令牌只存哈希，创建后只显示一次，绝不进日志
  • 鉴权失败、权限不足的响应不泄露任何内部信息
  • 所有外部输入都经过校验：URL、文件名、参数、长度
  • 出站请求有 SSRF 防护（协议白名单、IP 校验、禁自动重定向）
  • SQL 全部参数化，动态排序字段走白名单
  • 限流分用户/并发/渠道三个维度，有硬限也有软限
  • 多上游渠道有超时、熔断、自动切换和告警
  • 网关自己计量用量，账单以网关为准，定期和上游对账
  • 管理端点和管理员鉴权独立于用户体系
  • 环境变量缺了就快速失败，不提供默认密码

最后说点心态上的

做网关这一年，我最深的感受是：这类基础设施项目，前期 80% 的时间花在「看不见的地方」——鉴权、限流、对账、安全，每一项都不性感，但每一项漏了都会在某天夜里把你叫醒。

它不像写个酷炫的前端页面那样能立刻获得正反馈，更像是在修一条别人看不出来的下水道。但正因如此，一旦你把下水道修好，后面所有建在上面的东西都会稳稳当当。

如果你也在做类似的事，希望这份复盘能帮你少通几个宵。如果看完觉得「这也太麻烦了」——那也很正常，说明你还没被真实流量和真实账单教育过。等被教育过，你会回来把这篇翻出来再读一遍的。
