Anycast 的代价：全球负载均衡为什么不能只看"最近"

작성일2026-09-13|수정일2026-09-13|云计算
|조회수:

Anycast 的代价：全球负载均衡为什么不能只看”最近”

Anycast 在边缘平台里几乎被当作一个”免费好事”来介绍：同一个 IP 在很多地方宣告，用户自动连到最近的节点，延迟低、抗打击。但只要你真正运营过边缘上的业务，就会遇到一批典型症状：同一时刻不同用户的体验差距很大、灰度发布的流量比例总是与预期不符、某个区域”莫名”一起变慢。这些问题有一个共同根源——Anycast 不是负载均衡器，它是路由协议的一种使用方式。

代价一：路由是一种协商，而不是一种指令

关键认知是：BGP 路由的去向由对端运营商决定，而不是由你决定。你只能宣告”我在这里也有这个网段”；至于流量走不走这里，取决于对方的本地优先级、链路成本、对等协议与聚合策略。

因此会出现一些看似矛盾的现象：

  • 你的所有 PoP 都是健康的，但某个区域的流量持续集中到两个 PoP，导致这两个 PoP 承压；
  • 你新上线了一个 PoP，但一个月内几乎没有流量进来——因为对方运营商没有理由改路由；
  • 你下线一个 PoP，部分运营商立即切走，另一些则在很长时间内还在往旧地址发包。

结论很硬：Anycast 提供的是可达性与收敛性，不提供容量均衡。容量均衡必须由上层机制（DNS 负载、区域路由、限流）补足。

代价二：流量倾斜与”沉默的过载”

流量倾斜在正常运营中很常见。它的危险之处在于监控指标会被平均掉：全球视角看 CPU 与错误率都很健康，但某两个 PoP 的实际负载是均值的数倍，一旦遇到突发就会率先抖动。

有效的做法是把监控按 PoP 维度拆开，并且使用分位数而不是均值：

  • colo 维度拆分 P50/P95/P99 执行时长；
  • colo 维度拆分错误率，而不是只看全局错误率；
  • 关注”单 PoP 请求占比”，一旦某个 PoP 占比异常升高，视为容量风险信号；
  • 对”长尾 PoP”单独设阈值，因为它们的样本量小、噪声大，容易被均值掩盖。

排障提示：当用户反馈”只有我们公司访问慢”，且你无法在全局指标上复现时，第一步应该是让用户提供一次请求的 colo 值（或客户端返回的 cf-ray）。地域性问题在 PoP 维度上往往一目了然。

代价三：会话一致性与”路径变化”

Anycast 的路径不是固定的。网络调整、维护窗口、链路质量变化都可能改变某个客户端被路由到的 PoP。对无状态请求这没有影响；但对以下场景就是问题：

  1. 有状态会话：会话存在某个 PoP 的本地内存里，路径一变就”登录状态丢失”；
  2. 连接池：长连接一旦被重路由，TCP 层就需要重建；
  3. 客户端 IP 与边缘状态绑定：如果状态与源 IP 绑定，重路由会导致状态查询失败。

解决思路不是”让路径别变”（做不到），而是把状态从 PoP 本地移出。这一点在 Workers 上体现得特别明显：平台的运行时本身就假设你可能在不同地点执行，所以你不应该把会话放进模块级变量并依赖它跨请求存在。

代价是每次请求多一次存储往返。这就是边缘架构的经典取舍：用一次额外的存储 RTT，换取位置无关的正确性。

代价四：故障收敛的时间尺度不对称

Anycast 常被宣传为”故障自动绕行”。这说法方向正确，但时间尺度需要澄清：

  • 你的 PoP 宕机 → 宣告撤销 → 上游路由器更新路由表。收敛通常在秒级到数十秒级；
  • 你的 Worker 代码抛错 → 这不是路由问题，BGP 不会绕行，请求会持续失败；
  • 上游源站宕机 → 与 Anycast 无关，边缘会持续回源失败；
  • 单运营商链路劣化 → 可能不触发撤销，只是变慢。

这个不对称非常重要，它意味着：Anycast 只解决”节点级可达性故障”，不解决”应用级故障”。应用级高可用仍然要靠多区域部署、健康检查与自动降级来实现。

三种路由手段的对比

手段 决策层级 生效速度 粒度 适用场景
Anycast + BGP 运营商骨干网 秒级~分钟级 网段 基础可达性、抗节点故障
平台区域路由 边缘平台规则 毫秒级（每请求） 请求 灰度发布、区域化逻辑
DNS 地理解析 递归解析器 受 TTL 限制，分钟级 解析器缓存粒度 粗粒度分流、容灾切换

注意第二行的关键差异：平台内的区域路由是每请求决策的，因此不受 DNS 缓存影响。这就是为什么现代边缘平台上的”灰度发布”通常不用 DNS 权重来实现——DNS 权重在应用层表现为极不均匀的流量分布，且无法感知请求级特征。

实用做法：不要对抗 Anycast，而是在它之上做策略

把 Anycast 当作不可控的底座，在其上叠加可控的决策层，这是一条更稳的路线：

  1. 用平台属性而不是自建 GeoIP：request.cf.country、colo 是由平台维护的，比你自己维护 IP 库可靠。
  2. 灰度基于请求特征而非 IP：用 Header、Cookie、用户 ID 哈希做分流，比例可控且可复现。
  3. 热点写入避免集中在单键：不同区域同时写同一键，会形成跨区域的写入竞争，宁可分区。
  4. 对延迟敏感路径做减跳：把最靠近用户的决策（鉴权、缓存判定、路由）放在边缘，把重计算放回源。
  5. PoP 维度监控常态化：这是发现倾斜的唯一有效手段。

结语

Anycast 的价值在于”不需要中心调度就能获得全球可达性与抗打击能力”，这在工程上极其划算。但它的边界必须清楚：它不保证均衡，不保证路径稳定，也不解决应用故障。把这三件事想清楚，你就能判断哪些需求应该交给 Anycast，哪些必须自己在上层补一层策略。
