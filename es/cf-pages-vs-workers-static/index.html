Pages 与 Workers 的边界在哪里：静态托管选型的技术判断

Pages 与 Workers 的边界在哪里：静态托管选型的技术判断

Cloudflare 的 Pages 和 Workers 曾经界限分明：Pages 管静态站点，Workers 管动态逻辑。随着两者能力互相渗透——Pages 有了 Functions，Workers 有了静态资源绑定——这条线变得模糊，选型问题也从”该用哪个”变成了”哪个更省心”。

本文不站队，而是给出四个可判断的维度。在多数真实项目里，答案不是二选一，而是”主用哪个 + 另一个补位”。

维度一：构建模型决定工作流的形状

这是两者最本质的差异，也是最多人忽略的一点。

Pages 是构建驱动的。它假设你有一个需要编译的前端项目，平台负责检出代码、装依赖、跑构建命令、上传产物。这套模型天然适配 Git 工作流：push 即部署，PR 即预览。

Workers 是产物驱动的。它接收的是已经准备好的代码包（或资源目录），部署是 wrangler deploy 这一步，构建发生在你的机器或 CI 上。平台不关心你怎么生成产物。

这个差异带来的实际影响是：

关注点 Pages Workers
构建发生在哪 平台构建容器 你的本地或 CI
预览部署 内建，按分支自动生成 需自行编排或使用平台能力
构建耗时可控性 受平台约束 完全自控
适配非 Git 流程 较弱 很强

如果你的团队已经在 CI 里做完整的构建与测试，Workers 的产物驱动模型反而更自然——你不需要让平台再理解一遍你的构建。

维度二：运行时约束决定上限

两者都跑在边缘运行时上，但绑定与配置的默认姿态不同。

  • 启动与冷启动：边缘运行时通常没有传统意义上的长冷启动，但首次请求的初始化成本依然存在，尤其是加载大依赖或建立连接时。
  • CPU 时间：计费上通常区分 CPU 时间与墙钟时间，等待 I/O 的时间一般不计入 CPU，但长任务仍受总时长约束。
  • 状态：边缘运行时默认无状态，持久化必须走 KV、D1、R2、Durable Objects 等绑定。
  • 子请求:对外部服务的调用数量与并发存在约束，批量扇出需要谨慎设计。

对静态站点而言这些约束几乎不构成问题；对需要处理上传、调用多个上游 API 的应用，约束会迅速变成架构约束。

维度三：路由与中间件的表达力

静态托管最常遇到的”就差一点”需求是路由：把 /old/* 重定向、给 /api/* 加鉴权、按 Accept 头返回不同格式。这些需求在纯静态方案里靠配置文件，在 Workers 里靠代码。

一个是声明式的、有限表达力的路由表；一个是图灵完备的代码。前者更安全、更易审计，后者更灵活、更难约束。

实践中的分界线大致是：

  • 规则数量少、逻辑简单、变更不频繁 → 声明式路由更合适。
  • 需要读取请求内容做判断、需要访问绑定、需要重写响应体 → 只能用代码。

反过来，如果只是 302 一批旧链接，用 Workers 写代码是过度设计，而且会增加故障面：代码会抛异常，配置文件基本不会。

维度四：运维成本与团队认知

技术选型的最后一公里往往是人的问题。

Pages 的优势在于心智负担低：非前端工程师也能理解”push 就部署”。Workers 的优势在于可观测性强：你有完整的代码路径，可以在本地跑、可以单元测试、可以在 CI 里做集成测试。

团队特征 倾向 理由
前端为主，无专职运维 Pages 工作流内建，无需编排
有成熟 CI，追求可复现 Workers 产物驱动，构建完全自控
需要多环境灰度 两者皆可 + 明确约定 取决于是否愿意自建编排
需要长事务与队列 Workers + 队列能力 静态托管无法承载

混合架构：怎样组合才不别扭

现实中更常见的答案是混合，但混合有正确姿势和错误姿势。

正确姿势：静态产物交给 Pages（或 Workers 静态资源），动态接口交给 Workers，两者通过同域路由聚合。这样静态部分享受构建流水线，动态部分享受代码灵活性。

错误姿势：在 Pages Functions 里塞进整套业务逻辑，最后发现需要队列、需要长任务、需要复杂绑定，于是把一半逻辑迁移到 Workers，剩下的一半留在 Functions 里——两套部署、两套配置、两套日志，认知成本翻倍。

判断混合是否健康的标准很简单：如果两个部分的部署频率不同、依赖的团队不同、变更的理由不同，那它们就应该是两个独立的部署单元；反之，如果它们总是一起改，分包只会增加摩擦。

上面这个模式实际上在消解”Pages 还是 Workers”的二分法：一个部署单元同时拥有静态能力和动态能力，代价是你需要自己承担构建与部署编排。

判断法则：先问”我的构建流水线由谁负责”，再问”我的运行期配置由谁注入”。这两个问题的答案如果不同，说明你需要两个部署单元，而不是一个更复杂的单元。

结语：边界在收敛，判断标准不变

平台能力的收敛会让”功能对比表”越来越没意义，因为两边最终会看起来都支持。但判断标准其实很稳定：构建发生在哪、配置在何时注入、路由由谁表达、谁来维护。把这四个问题答清楚，选型就不再是风格偏好问题。

如果非要给一个默认建议：以静态内容为主的站点，从 Pages 起步，遇到明确的运行期需求再引入 Workers；以 API 与动态逻辑为主的场景，直接从 Workers 起步，把静态资源当作它的一个绑定。这样两条路径都不会在一开始就背上不必要的复杂度。

说明： 本文讨论的是架构选型方法而非产品功能承诺，Pages 与 Workers 的具体能力、配额与命名可能随版本演进而变化，请以 Cloudflare 官方最新文档为准。文中倾向性结论为笔者基于工程实践的主观判断，不同团队应按自身约束重新评估。
