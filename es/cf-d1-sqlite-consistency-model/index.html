D1 与 SQLite 的读副本一致性模型：延迟、顺序与故障恢复

把数据库搬到边缘，第一个被现实击碎的美好幻想往往不是性能，而是「为什么我刚刚写入的数据查不到了」。这不是 D1 的 bug，而是分布式系统里读副本一致性模型在所有边缘数据库上的必然表现。本文不谈怎么建表，只谈一件事：当一次写操作返回成功之后，世界各地的读者究竟在多长时间里、在多远的距离上，能看到一个「什么样」的数据版本。

为什么边缘读会「看不到」刚写的行

D1 的架构本质上是「一个主库 + 一组读副本」，主库负责所有写入，读副本分布在离用户更近的位置负责读取。这个模型决定了写入必须先落到主库并被确认提交，随后才通过复制通道投递到各副本。任何读副本上的查询，返回的都是某个已经复制完成的快照，而不是主库此刻的真实状态。

因此「写后立即读」在边缘会遇到一个明确的窗口期：写请求的响应在网络里返回给客户端的同一时刻，复制流可能还停在离主库最近的节点上。用户刷新页面，请求被路由到一个尚未追上进度的副本，于是看到了旧值。这个窗口通常以毫秒到百毫秒量级计，但它不是零，也不是固定值——它取决于主库到副本的物理距离、复制管道的拥塞情况和当时的写入压力。

一个常见的错误认知是「我把两次请求都发到同一个边缘节点，就能保证顺序」。事实并非如此：边缘节点只是客户端到网络的入口，它到主库与到副本的链路是独立的。即使入口相同，写走主库路径、读走副本路径，两者依然是两条不同的数据路径。想在这条路径上要顺序性，必须显式地把读也钉到主库。

会话令牌：把「读到自己写」变成可工程化的保证

Cloudflare 在 D1 的 HTTP 接口与 Workers Binding 中提供了会话（session）与书签（bookmark）机制，用来解决上述「读己之写」（read-your-writes）问题。它的思路很朴素：写入时返回一个书签，代表主库当前的复制位置；后续读取时把这个书签带上，副本会等到自己至少追平到该位置后再返回结果。

这段代码里有两个关键选择。第一，withSession 的参数从 first-primary 变成书签之后，读取的语义从「哪快读哪」变成了「至少不早于这个点」。第二，书签是可以跨请求传递的普通字符串，这意味着你可以在服务端存储、在 Cookie 里携带、甚至写进响应头，让同一个用户的后续读请求都获得顺序保证。

代价必须讲清楚：带上书签的读会被强制等待复制追平。如果你的书签很新，而请求被路由到了很远或很忙的副本，这次读的延迟会比普通读高出一个量级。所以书签适合用在「用户自己刚写入、然后马上要看结果」这种强相关场景，而不是用在全站的列表页查询上。

顺序一致性在什么条件下被破坏

「读己之写」是单用户视角的顺序性。一旦视角扩大到多用户，问题就复杂得多。假设 A 用户发表一条评论，B 用户在同一秒打开页面，B 的读大概率落在没有这条评论的快照上。这不是错误，而是最终一致性的定义本身。

真正会变成事故的是下面几种顺序错乱：

  • 跨表因果断裂：事务里同时写了主表和统计表，如果事务本身没有被原子地应用到副本，可能出现主表已更新、统计表还是旧值的中间态。SQLite 在单库内是原子提交的，但复制投递的粒度与可见性边界需要以官方文档为准。
  • 回滚导致的「时间倒流」：某些故障切换或重建副本的场景会让副本的进度短暂后退，用户刚看到的新数据又消失了。这类现象通常伴随主库故障转移，属于低频高风险事件。
  • 读缓存与副本叠加：在 D1 前面又套一层 KV 或 HTTP 缓存，缓存自身的 TTL 会让一致性窗口被放大数倍。很多「D1 不一致」的投诉，根因其实在外层缓存。

理解这一点很重要：一致性不是数据库单方面提供的属性，而是整条读路径共同决定的结果。数据库上的一致性能力再强，也挡不住你在前面叠一层无脑缓存的缓存。

主库故障切换与数据可见性回退

D1 作为托管服务，会在主库所在区域出现问题时进行故障转移。对应用而言，最需要提前设计的两件事是写入的可重试性和读取的容忍度。

写方面，网络抖动会导致「服务端已提交但客户端未收到响应」，这个经典的两难在边缘场景更容易出现，因为链路上还多了一层边缘节点。幂等键是唯一稳妥的解法：客户端为每次写生成一个唯一 ID 并在重试时复用，服务端对这个 ID 做去重。

读方面，要接受一个事实：在最坏情况下，副本可能落后于你上次读到的位置。因此不要把「上次读到的数据」当作业务上的既成事实来做后续决策。举一个具体例子：不要用「读到的余额大于 0」作为发起扣款的理由，而应该把判断放到主库上的原子条件更新里。

下面这张表对比了几种读取策略在延迟、一致性和适用场景上的差异，可以作为选型参考。

读取策略 一致性保证 典型延迟量级 适用场景
默认副本读 最终一致 最低（就近命中） 列表页、静态内容、统计展示
带书签的副本读 读己之写 中等，视落后程度 用户提交后立即回显
强制主库读 强一致（单主） 较高，跨区域 余额、库存、权限判定
副本读 + 外层缓存 弱于最终一致 最低 可接受陈旧的聚合数据

经验法则：把「读己之写」写进需求文档，把强一致读限制在极少数关键路径上，剩下的全部按最终一致设计。反过来做，边缘带来的延迟优势会被等待复制的时间吃回去。

从故障排查倒推一致性设计

线上反馈「数据不对」时，排查顺序建议固定成下面四步，能省掉大量无谓的怀疑：

  1. 确认读路径：这条查询究竟走的是副本还是主库？先看请求被路由到了哪里，再看代码里用的是默认读还是会话读。
  2. 确认外层缓存：D1 前面有没有 KV、Cache API 或 CDN 缓存？如果有，先绕过它再复现一次。
  3. 确认时间窗口：写入与读取相隔多久？几十毫秒内的问题大概率是复制延迟，不是逻辑错误。
  4. 确认是否发生故障转移：查询监控里主库是否在问题时段有切换记录，切换会导致可见性回退。

这套顺序的价值在于：它把「玄学不一致」拆成了四个可观测、可证伪的假设。绝大多数情况下，问题在前两步就能定位。

团队落地时的边界约定

最后是一组工程约定，建议写进团队规范里：

  • 所有写入接口必须返回可传递的书签，前端在关键回显场景携带它。
  • 所有关键判断不得基于副本读的绝对值，必须基于主库上的条件更新。
  • 明确列出允许陈旧的字段清单，其余字段一律不允许出现在默认副本读的结果里。
  • 监控复制延迟与故障转移事件，把它们当作一级告警而不是后台信息。

把一致性当作一个显式的架构决策而不是默认假设，是团队从「能跑通」走向「能上量」的分水岭。
