D1 成本与配额模型拆解：行读写、存储与按量计费的隐藏成本

D1 成本与配额模型拆解：行读写、存储与按量计费的隐藏成本

在传统关系型数据库里，估算成本主要看实例规格和并发连接数，SQL 写得好不好通常不影响账单。到了边缘托管的 SQLite 方案上，这套直觉会失效：D1 的计费核心是行读写次数与存储量，而不是实例规格。这意味着一次慢查询和一次快查询可能同价，而一次被索引优化掉的扫描和一次全表扫描可能差出好几个数量级。理解这个模型，是控制成本的前提。

计费维度到底看什么

按公开的计费口径，D1 的费用主要由几块构成：读操作触及的行数、写操作触及的行数、存储的数据量与备份占用、以及超出免费额度后的按量费用。不同套餐在额度、并发和可用能力上有差别，具体数值以官方定价页为准。本文关心的是这些维度背后的行为机制，而不是记住一串会变的数字。

需要特别理解的一点是「行」这个计量单位。一条 SELECT 如果通过索引精确定位到一行，成本约等于一次行读；如果它退化成全表扫描，扫过的每一行都可能计入读行数。所以在 D1 上，索引不是性能优化，而是成本优化。这跟传统数据库里「索引主要为了快」的心智模型有本质区别。

写操作同理。单行 INSERT 计一次写；如果表上有触发器或者外键级联，间接影响的行也可能被计入。批量插入 N 行，写行数通常是 N 而不是 1。这些规则看起来直白，但在嵌套结构、级联删除和 upsert 场景里很容易被低估。

查询次数与行数的分离：一个反直觉的例子

看下面两个语义等价、成本却可能差出几十倍的写法。

写法 A 在应用层循环执行时，每次循环都要重新走一遍网络与查询解析，如果循环里还带上了表扫描，读行数会随评论数量线性增长。写法 B 的读行数上界主要由参与结果集的行数决定，配合 comments(post_id, created_at) 这样的复合索引，扫描范围可以被压到接近 LIMIT 的大小。

这不是说 JOIN 永远更便宜。当结果集很大、或者连接条件无法走索引时，一次 JOIN 扫描的行数可能比多次点查更大。真正的原则是：先算清楚每种写法的行触达量，再决定形态，而不是背「JOIN 更快」或者「点查更省」这类口号。

索引的双面性：省读行，涨写成本

索引把读成本压下去的同时，会抬高写成本。每插入一行，所有相关索引都需要维护，这会体现为额外的写操作开销，同时占用存储。在 D1 这种按行计费的模型里，索引的净收益取决于读写比。

判断一个索引是否值得，可以用下面这张表做快速对照。它把几类常见索引按收益与代价分档，方便在评审时快速决策。

索引类型 读收益 写代价 适用判断
高频等值查询列 高，可直接定位行 低，单列维护 几乎总是值得
复合索引（前导列高频） 高，可覆盖范围扫描 中，列多则维护成本上升 有明确查询模式时值得
低区分度列（如布尔位） 低，选择性差 低但无收益 通常不值得，删掉
纯写表的索引 无读需求 高，纯增负担 审计类表应尽量少建
覆盖索引 高，可避免回表 中到高，存储占用大 热点查询值得

一个常被忽略的点是低区分度索引。给 status 这种只有几个取值的列单独建索引，优化器很可能根本不选它，但每次写入都要维护它。这类索引是纯成本，审计时应该优先清理。

批量写入与小事务的取舍

写成本与「写行数」挂钩，这让批量写入看起来是省钱利器——一次请求提交 1000 行，比 1000 次请求各提交 1 行省掉了大量网络往返和请求开销。这个方向是对的，但有两个边界必须注意。

第一是事务体量上限。单次事务过大可能触及服务端的限制，具体阈值以官方文档为准。稳妥的做法是按几百到一千行分批，而不是一次灌入几万行。

第二是失败代价。一次提交 1000 行的事务失败，重试意味着全部 1000 行的写开销重新计一遍（在服务端已经部分写入的情况下尤其如此）。所以分批大小需要与幂等设计配合，让重试不会产生重复数据。

ON CONFLICT DO UPDATE 在这个场景里很实用：它把「先查是否存在再决定插入还是更新」的两步逻辑压成一步，省掉了那一次判定用的读行。这是一个典型的「用写法换成本」的例子。

存储、备份与那些不显眼的费用

除了行读写，还有几项容易被漏算的成本：

  • 存储量：按实际数据体积计费。文本表长期只增不删，体积会缓慢膨胀，需要归档策略。
  • 备份与时间点恢复：保留策略越长，占用与成本越高。多数团队并不需要很长的保留窗口。
  • 导出与迁移流量：把数据导出到对象存储做分析时会产生传输与请求开销，规划时要一并算进去。
  • 闲置额度：套餐内额度不会结转，低峰期省钱、高峰期超支是常态，预算应按峰值估算。

一条实用经验：先用「每千次请求的预估行触达量」乘以峰值 QPS，估算月度成本量级，再和免费额度对照。先把量级算对，比精确到分钱更重要——量级错了，优化方向一定是错的。

把成本压下来的惯用手法

下面这些手法在多数边缘数据库项目里都适用，按收益从高到低排列：

  1. 给热点查询建对索引，尤其是带 LIMIT 的分页查询，让扫描范围与返回行数同阶。
  2. 消灭 N+1，把循环里的点查合并成一次批量查询或一次 JOIN。
  3. 用 upsert 替代「查后写」，省掉判定所需的读行。
  4. 读走缓存，把可容忍陈旧的读取放到 KV 或 Cache API 上，让 D1 只承接需要一致性的查询。
  5. 写入分片批量化，按几百行一批提交，同时保证幂等。
  6. 定期清理低区分度索引，把纯写负担去掉。
  7. 给只增表加归档，把历史数据搬到对象存储，保持主表体积可控。

这七条里，前三条通常能解决大部分超支问题，后四条属于长期治理。团队的评审清单里应该固化前三条，把它们当作代码合并的硬要求。

成本模型对架构的反向塑造

理解 D1 的计费方式之后，一些架构选择会变得显而易见。比如：

  • 聚合统计不放在 D1 上实时算。全表聚合意味着读行数等于表大小，次数一多账单会失控。更好的做法是周期性把结果物化到小表，或者干脆放进 KV 做读缓存。
  • 日志与审计数据不进主库。这类数据只需要写不需要就地查，放到对象存储更合适，D1 只保留必要索引。
  • 把「读多写少」和「写多读少」拆开。前者适合放 D1 加缓存，后者也许更适合直接落对象存储再离线分析。

换句话说，成本模型不只是财务问题，它会一路影响你的表设计、查询写法和模块拆分。越早把这个模型引入架构评审，后期的返工越少。
